# Server Resource Guardian 开发进展报告

**日期**:2026-09-24 · **环境**:WSL2 一次性实验环境(4 vCPU / 3.8GiB + 2GiB swap,内核 6.6+)
**性质**:本地可丢弃环境验证,未触碰任何生产系统

---

## 一、项目要解决什么问题

服务器在资源被压垮(CPU/内存/磁盘爆满)时,管理员面临三个真实困境:

1. **进不去** — SSH 登录失败,人被锁在系统外,只能重启(业务全停)
2. **看不清** — 监控工具(Beszel 等)自身也被压垮,告警失效,谁也不知道出了什么事
3. **找不到** — 好不容易进去了,在系统抖动里翻找真凶进程可能要十几分钟,还可能找错

**Server Resource Guardian 的定位**:在上述极端条件下,保证 ①告警及时送达;②管理员能进得来;③进来后能快速准确定位压力源,协助完成处置闭环。

---

## 二、本轮完成的核心工作

### 2.1 定位并解决了"进不去"的根因(层一)

**根因发现**:资源爆满时 SSH 进不去,不是因为内存不够分,而是内核的 OOM(内存耗尽杀手)机制"出手太晚" — 它要等内存彻底耗尽才行动,而行动前会疯狂读写交换分区(swap 碾轧)数十秒到数分钟,**这段时间服务器对一切新连接失去响应**。调内核参数无法解决(实验证实无效),这是机制问题。

**解决方案**:部署用户态早杀机制 earlyoom — 在内存可用量跌破 10% 时就提前清除压力源,根本不让系统进入"碾轧区"。配合三层纵深防御(登录路径保护、管理员内存储备、降低换页激进度)。

**效果(同一极端压力下复测)**:

| 配置 | SSH 进入成功率 |
| --- | --- |
| 无防御(基线) | 19/40(**52.5% 失败**) |
| 仅调内核参数 | 20/40(无改善,证实机制问题) |
| **+ 早杀机制(最终方案)** | **40/40(100%),且延迟接近正常水平** |

### 2.2 量化了"看不清、找不到"的改善(层二)

模拟真实运维场景:管理员从发现问题到完成定位处置的全流程计时。

| 指标 | 无 Guardian(人工盲找) | 有 Guardian | 改善 |
| --- | --- | --- | --- |
| 总任务时长(MTTA) | 1106-1160 秒(~18-19 分钟) | **42 秒** | **~26 倍** |
| 定位准确率 | **0/2(两轮都找错目标)** | 精确到容器 ID | 正确性差距 |
| 压力出现→告警送达(MTTD) | 无告警,靠人发现 | **5-9 秒** | 管理员未开终端已知出事 |
| 登录后→定位目标(MTTI) | 层层排查数分钟 | **0.07 秒**(一步定位) | 70 倍优于通过线 |

### 2.3 消除了监控系统自身成为负担的问题(观察者效应)

**此前发现的真实缺陷**(EXP-088):压力最高时,Guardian 自己的观测行为反而与人工操作抢资源,使 docker 操作劣化 **21 倍**(11.7s→190.5s)— 监控系统帮倒忙。

**本轮修复**:压力门控机制(系统检测到自身处于高压时自动降级观测频率)+ 告警网关架构重构(读写解耦,修复风暴中告警丢失缺陷)。

**修复后实测**:观察者效应 **0.70x**(不仅无劣化,反而比无 Guardian 略快)— 从 21 倍负收益翻转为正收益。

### 2.4 最严酷场景验证:三资源同时爆满

CPU(4 核钉满)+ 内存(6.7GiB 需求 vs 5.8GiB 供给)+ 磁盘(持续同步写风暴)**三者同时压满**,检验系统生存能力:

| 指标 | 基线(全部关闭) | 有 Guardian + 防御栈 | 差距 |
| --- | --- | --- | --- |
| SSH 进入成功率 | **8/20(40%)** | **19/20(95%)** | 2.4 倍 |
| 连上后的操作延迟 | 慢 3.3 倍 | 接近正常 | — |
| docker stats 单步操作 | **241 秒** | 2.7 秒 | **90 倍** |
| 宿主宕机 | 否 | 否 | 两者均扛住 |
| 告警 | 全部失效 | 三种资源 CRITICAL 全部送达 | — |

**结论**:三资源爆满不会宕机,但基线下管理员处于"半失联"状态(四成概率进不去,进去了单步操作要等 4 分钟)。Guardian + 防御栈将这条生命通道恢复到 95% 进入 + 秒级操作。

**附带发现并修复**:实验暴露 WSL 平台默认配置的一个缺陷(用户会话管理器的 OOM 优先级被系统设为"比压力源更先被杀"),已用一行配置修复并验证。
