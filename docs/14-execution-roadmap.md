# 执行路线蓝图

更新时间：2026-09-19

> 本文档是项目的总执行蓝图：确定技术路线、执行阶段和测试方式。所有 [Goal](../goals/README.md) 按本蓝图推进；蓝图与某份具体方案文档冲突时，以本蓝图的技术路线定调为准，并把差异回填到具体文档。

## 1. 技术路线定调

**项目主线是“发现宕机风险并自动处理”，不是给所有 Docker 容器统一设置资源上限。** Beszel 负责监控基础，Guardian 负责本机实时风险检测、对象定位、策略判断、分级处置和恢复验证；现成机制优先复用，只有在安全策略和处置流程存在明确缺口时才开发 Guardian 能力。

Docker/systemd/cgroup 资源限制属于**按业务允许时使用的可选预防性隔离手段**。它可能改变应用行为、触发应用内 OOM 或影响缓存/突发负载，不能作为所有容器的默认配置，也不是本项目的统一验收目标。

路线按职责分层：

| 层 | 能力 | 技术选型 | 当前状态 |
| --- | --- | --- | --- |
| 观测层 | 指标采集、历史、可视化和常规告警 | Beszel Hub + Agent（0.19.0） | Mac Multipass 已部署；Goal 6 待完成指标验收 |
| 检测层 | 秒级识别主机/容器接近宕机的风险和趋势 | Guardian 读取 `/proc`、PSI、cgroup、Docker stats/events 等 | 第一版已实现；Goal 6 负责与 Beszel 对照联调 |
| 决策层 | 对象归属、保护名单、允许动作、冷却和熔断 | 配置化策略；默认 `observe` | 第一版已实现；Goal 6 负责事件契约和 Adapter |
| 处置层 | 快照、通知、优雅动作、受控终止和恢复验证 | Docker/systemd API、服务适配器、审计日志 | 本地可丢弃对象闭环已验证；集成联调待完成 |
| 可选隔离层 | 对明确允许的业务设置资源边界 | Docker/systemd/cgroup | 业务按需采用，不作统一要求 |

## 2. 为什么以 Beszel 为基础

- 公司已在用 Beszel，复用可避免重复建设 Prometheus/Grafana 等第二套监控平台。
- Beszel 已覆盖主机 CPU、内存、swap、磁盘、I/O、网络、load，以及 Docker 容器与 systemd 服务状态和历史数据。
- Beszel 通信只传输监控数据、不执行命令，因此监控通路与处置通路天然解耦。Beszel 不能承担秒级危机处置触发，实时检测和动作执行需要本机策略组件负责。
- 资源限制只在应用明确允许时作为隔离手段使用，不把“容器有内存上限”当作自动处置的前提。
- Beszel 已在历史 WSL2 和当前 Mac Multipass 隔离部署 0.19.0；当前 Mac Hub/Agent 认证通过、容器 healthy。

## 3. 测试方式（固定）

- 当前主测试环境：Apple Silicon Mac 上的 Multipass Ubuntu 22.04.5 ARM64（2 vCPU、4GB 内存、systemd 249、内核 5.15、cgroup v2、Docker 29.1.3）。
- Goal 1–3 的历史实验仍在 Windows WSL2（Ubuntu 26.04.1、systemd 259、内核 6.18）中完成；历史结论不改写为 Mac 实验。
- ARM64 虚拟机负责功能、流程和有界压力验证；生产若为 x86_64，需在获授权的 x86_64 Ubuntu 22.04 测试机上完成最终兼容性复核。
- 自动处置实验必须使用可丢弃测试对象，先验证 `observe` 和 `simulate`，再经过授权进入 `enforce`。
- 实验验收关注风险检测、对象定位、保护判断、动作结果和恢复验证；不以统一配置 Docker 资源限制作为验收条件。

## 4. 执行阶段与 Goal 映射

六个阶段串成一条路线，前一阶段是后一阶段的前提；生产交接是完成本地验证后的外部授权门：

| 阶段 | 对应 Goal | 内容 | 进入下一阶段的门 |
| --- | --- | --- | --- |
| 1 观测 PoC | Goal 1 | Beszel 指标完整性、开销和基础阈值校准 | 主机/Docker/systemd 指标可见且及时，结论有实验记录 |
| 2 救援韧性 | Goal 2 | 高压下 SSH、诊断和停止任务链路验证 | 明确系统在高压下的韧性、失效条件和生产复核项 |
| 3 自动处置评估 | Goal 3 | 现成机制、风险检测和检测-定位-处置-恢复管道评估 | 明确现成能力、自动处置缺口和安全边界 |
| 4 Guardian 最小实现 | Goal 4 | 实时检测、策略判断、快照、分级动作、恢复验证和受控灰度 | 在可丢弃对象上完成闭环，并通过授权后的安全验收 |
| 5 本地生产仿真报告 | Goal 5 | 复刻生产关键运行时、容器角色、压力模式和 Guardian 对照结果 | 报告完成，明确本地实测、容量推断和生产待复核边界 |
| 6 Beszel 二次开发集成 | Goal 6 | 指标验收、只读 Adapter、双路径对照、Guardian 联调和 UI 集成方案 | 完成本地集成证据后再评估受控 enforce |

Goal 6 完成后，不直接进入生产动作；下一道门是取得非生产 x86_64 Ubuntu 22.04 测试机和明确的观测/动作授权。

## 5. 边界与安全

- `observe` 是默认模式；不默认启用自动终止、重启容器或资源变更。
- `simulate` 用于验证对象选择、动作计划和审计记录；`enforce` 只有在测试对象、保护名单、允许动作和授权齐备后才能使用。
- 自动处置不等于统一限流。Docker/systemd 资源限制只有在具体业务确认兼容时才采用。
- 不在未获授权时对生产环境注入 CPU、内存、I/O 或网络故障。
- 本地 WSL2 结论只代表本地环境，不直接作为生产阈值或兼容性结论。
- 计划不等于事实；实验结论统一进入 `experiments/EXP-###`，失败实验同样保留。
