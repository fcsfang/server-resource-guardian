# 执行路线蓝图

更新时间：2026-09-18

> 本文档是项目的总执行蓝图：确定技术路线、执行阶段和测试方式。所有 [Goal](../goals/README.md) 按本蓝图推进；蓝图与某份具体方案文档冲突时，以本蓝图的技术路线定调为准，并把差异回填到具体文档。

## 1. 技术路线定调

**以 Beszel 为监控平台基础**：监控用 Beszel 一条主干，救援与自动保护优先复用现成机制，只有在现成能力出现明确缺口时才开发轻量 Guardian。不重新搭建 Prometheus/Grafana，不先开发一套完整平台。

路线分四层，自下而上：

| 层 | 能力 | 技术选型 | 当前状态 |
| --- | --- | --- | --- |
| 监控层 | 指标采集、历史、告警 | Beszel Hub + Agent（0.19.0） | 已部署上线（WSL2） |
| 救援层（第一层） | 资源高压下保留 SSH 救援链路 | systemd/cgroup + Docker 资源边界（CPU 权重/配额、内存保护） | 待验证 |
| 自动保护层（第二层） | 无人及时操作时按规则受控止损 | 先评估 systemd-oomd、Monit、Docker/systemd 限制 | 待评估 |
| 自研层（兜底） | 本机快照 + 受控处置 | Guardian（轻量守护服务） | 仅在缺口明确时开发 |

## 2. 为什么以 Beszel 为基础

- 公司已在用 Beszel，复用可避免重复建设 Prometheus/Grafana 等第二套监控平台。
- Beszel 已覆盖主机 CPU、内存、swap、磁盘、I/O、网络、load，以及 Docker 容器与 systemd 服务状态和历史告警。
- Beszel 通信只传输监控数据、不执行命令，因此监控通路与处置通路天然解耦——处置能力单独用现成机制补齐，缺口才自研 Guardian。
- Beszel 已在当前电脑 WSL2 隔离部署 0.19.0，Hub/Agent 认证通过、容器 healthy。

## 3. 测试方式（固定）

- 环境：当前电脑 Windows + WSL2（Ubuntu 26.04.1、systemd 259、内核 6.18、Docker 29.1.3）。
- 所有 PoC 与实验统一在此 WSL2 环境进行，不另设独立测试机，除非外部测试授权到位。
- 版本差异：本地 systemd 与内核高于生产（systemd 259 vs 249、内核 6.18 vs 6.8），本地结论一律标注"本地验证"，生产兼容性需 Ubuntu 22.04 测试机复核——这是外部依赖，不阻塞本地先行。

## 4. 执行阶段与 Goal 映射

四个阶段串成一条路线，前一阶段是后一阶段的前提：

| 阶段 | 对应 Goal | 内容 | 进入下一阶段的门 |
| --- | --- | --- | --- |
| 1 只观测 PoC | Goal 1 | Beszel 指标完整性核验 + 受控压测 + 首轮本地阈值 | 主机/Docker/systemd 指标可见且及时，开销实测，阈值已建立 |
| 2 第一层救援 | Goal 2 | SSH 救援链路 + 资源边界（CPU/内存场景） | 高负载下"建连 → 诊断 → 停止任务"链路仍可用 |
| 3 第二层自动保护 | Goal 3 | systemd-oomd / Monit 等现成策略评估 | 现成能力覆盖范围与缺口已判定 |
| 4 缺口判定 | — | 现成足够则停；有明确缺口才评估 Guardian | 明确是否开发、开发什么 |

## 5. 边界与安全

- `observe` 是默认模式；不默认启用自动终止、重启容器或资源变更。
- 不在未获授权时对生产环境注入 CPU、内存、I/O 或网络故障。
- 本地 WSL2 结论只代表本地环境，不直接作为生产阈值或兼容性结论。
- 计划不等于事实；实验结论统一进入 `experiments/EXP-###`，失败实验同样保留。
