# 现成资源保护策略：调研与汇报重排建议

调研日期：2026-09-17。范围：以已有 Ubuntu 22.04 / systemd 249 / cgroup v2 / Docker 服务器为背景，比较可配置复用的自动资源治理策略。未在服务器部署、核验启用状态或压测。其他机器配置和真实故障来源仍待确认。

## 结论

应该先介绍现成保护策略，再讨论观测、候选选择和执行接口。已有方案不只提供接口，也包含触发、选择和执行逻辑。不过，“完整”必须限定保护对象和目标：systemd-oomd是内存压力应急处置方案，不是所有内存管理、应用根因诊断或业务恢复的完整系统。

策略有三类：持续施加资源边界；按已知对象配置条件与恢复动作；按压力动态选择牺牲对象或调度工作负载。三类可以组合，但不能不协调地部署多个独立执行器。

## 按资源比较

| 问题 | 可复用方案 | 自动策略 | 人需要配置什么 | 覆盖边界 |
| --- | --- | --- | --- | --- |
| 内存压力导致整机失去响应 | systemd-oomd | 检查PSI或swap条件，在符合条件的子cgroup中选择并SIGKILL | 监控层级、阈值、持续时间、排除/避免规则 | 内存应急；不提供温和退出、任意业务恢复验证 |
| 内存不足，按进程处理 | earlyoom | 检查可用内存和swap，按oom_score等选择进程并发送终止信号 | 阈值、进程偏好 | 进程与业务容器不是同一粒度；avoid是偏好，不应当作绝对保护 |
| 需要更灵活的内存保护策略 | Meta oomd | PSI/cgroup v2监控、规则与插件驱动动作 | 规则集、目标组、保护策略，缺口才扩展插件 | 独立于systemd-oomd；需评估构建、维护与适配成本 |
| 单个任务抢占CPU | Docker CPU限制 / systemd CPUQuota、CPUWeight（cgroup） | 内核按配额持续限制CPU时间，竞争时按权重分配 | 容器或服务预算、分组和权重 | 配额治理，不自动根据业务延迟选择杀谁；CPU高利用率未必异常 |
| 单个任务占满磁盘IO吞吐 | systemd IORead/WriteBandwidthMax、IOPSMax / cgroup io.max | 按设备和cgroup限制带宽或IOPS | 设备、组、限额 | IO吞吐控制，不释放磁盘空间；设备与文件系统上的实际生效需验证 |
| 日志持续增长占满磁盘 | Docker local日志驱动 / journald / logrotate | 文件大小、数量、保留时间等条件驱动轮转或清理 | 日志范围、大小、保留期、调度频率 | 各管自己的日志；不能判定任意业务文件可否删除 |
| 进程或线程数量失控 | Docker pids-limit / systemd TasksMax（cgroup pids） | 达上限时阻止继续创建任务 | 每个组的任务预算 | 防止继续增长，不自动杀掉已有任务；线程计数也影响上限 |
| 网络带宽被任务占满 | Linux tc，例如TBF | 按速率和突发预算整形，排队超预算流量 | 流量分类、出口位置、速率与队列 | 持续限流策略，不能自动决定业务优先级；入站治理与出口不同 |
| 固定服务CPU/内存异常或不响应 | Monit | 周期检查已知对象，满足持续条件后执行已配置的启停动作 | 对象、条件、动作、次数控制 | 有现成规则执行机制，但不是任意Docker容器的动态牺牲选择器 |
| 多节点容器资源压力 | Kubernetes kubelet | 内存、磁盘、inode、PID压力触发回收或Pod驱逐 | requests/limits、优先级、阈值与宽限期 | 必须由Kubernetes管理；节点压力驱逐不把CPU高占用作为同类驱逐信号 |
| 多用户离线CPU/内存/GPU任务争抢 | Slurm | 申请、排队、分配、cgroup约束及配置后的抢占 | 作业提交方式、资源声明、队列/QOS、约束与抢占策略 | 工作负载需纳入调度；不是安装后就接管任意现有Docker；暂停不释放内存和GPU分配 |

CPU、IO和PID限制本身由内核持续执行，不能把它们仅仅写成“需要程序反复调用的接口”，也不能把它们包装成自动识别故障并保证业务恢复的全套应急系统。

## systemd-oomd：针对systemd 249的核验

本轮读取Ubuntu Jammy的249系列手册，而非只引用最新版本。

- 触发：内存压力超过配置阈值并持续指定时间，或满足配置的内存与swap条件。PSI百分比表示阻塞时间比例，不是“内存使用百分比”。
- 选择：内存压力路径按回收活动量从高到低考虑符合条件的后代cgroup；swap路径按符合条件对象的swap用量考虑。不是通用的“选内存占用最大容器”。
- 执行：对选中cgroup下进程发送SIGKILL。不是Docker stop式的优雅退出。
- 管理范围：cgroup v2、PSI与内存记账是前提；swap推荐启用以给反应留出时间，无swap时压力路径仍可用但需调优。
- 保护设置：249手册已有ManagedOOMPreference=avoid/omit；avoid是在有其他候选时降低选择优先级，omit从该机制候选中排除。属性有属主等限制，且不会递归应用到下级cgroup，不能把父级设置直接视为整个子树的万能保护。
- auto不等于保护：即使某个单元配置为auto，祖先启用kill时仍可能成为候选。
- 与Docker结合：必须核验cgroup驱动、容器层级、业务分组、重启策略以及其他执行器，不能根据操作系统版本断言已经保护了所有容器。
- 它循环观察的是资源条件，不是公司关键业务的健康恢复。

因此，可优先介绍和试点评估，但还不能直接宣布生产选型。

## 磁盘方案需要拆开讲

磁盘空间和磁盘IO是不同问题。

Docker local日志驱动内置轮转与保留配置。更改daemon默认日志配置不会自动改变现有容器，迁移步骤要单独评估。不要用外部logrotate直接接管Docker私有日志文件。

journald的SystemMaxUse、SystemKeepFree约束journal自身；主要删除归档文件，不能保证其他业务占满磁盘后自动释放任意目标空间。

logrotate按已配置路径、周期或大小轮转，由定时调用实际触发；大小条件不是不依赖运行频率的实时硬上限。copytruncate存在丢失少量日志的窗口。

业务目录可考虑文件系统配额作为容量隔离，但需另核文件系统、挂载与存储驱动条件，不能写成所有Docker目录普遍可用的开关。是否删除业务文件仍需明确的所有权和保留规则。

## 面向当前五台Docker服务器的评估顺序

1. 盘点真实故障：区分内存压力、CPU竞争、IO延迟、日志增长、业务文件增长、PID或GPU资源争用；尚无事件证据，不预设根因。
2. 优先核验本机现成策略：容器CPU/内存/PID边界、日志轮转；内存应急评估systemd-oomd；固定服务恢复评估Monit。
3. 业务名单与策略配置先明确，再验证会否误伤关键服务、容器是否被自动拉起、压力和业务是否恢复。
4. 多用户离线任务若占主导，评估Slurm作为工作负载管理路线；已有或计划容器编排时再评估Kubernetes，不为了几个阈值直接推荐迁移。
5. 自研只补覆盖差距：应用保存进度接口、特殊业务优先级、跨资源组合判断、恢复验证与协调记录。缺口未核实前不估计开发量。

## PPT重排建议

背景与保护目标之后，先放“已有策略能解决什么”，将systemd-oomd从附录前移。建议正文依次为：

1. 问题与保护目标。
2. 现成策略全景：持续限额、按条件恢复、压力驱逐与作业调度。
3. 内存应急完整案例：systemd-oomd的触发、选择、动作和边界。
4. CPU/IO/PID与日志治理：配置后哪些自动执行，分别管理什么。
5. 当前Docker环境优先评估项；Kubernetes/Slurm作为有条件的管理路线。
6. 覆盖缺口与业务约束。
7. 为验证和补缺而展开观测、定位与处置；监控平台比较仍有意义，但不必成为每个现成保护策略的硬依赖。
