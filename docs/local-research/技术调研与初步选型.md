# 服务器资源保护：技术调研与初步选型

调研日期：2026-09-16  
状态：第一轮桌面调研；已确认 5 台性能有差异的服务器；参考机 Ubuntu 22.04.5、systemd 249、cgroup v2、Docker 29.1.3，等待事故样本及其余机器信息。  
范围：Ubuntu + Docker 是主线，Kubernetes 仅作为条件分支，未确认使用。上游 latest/main 文档可能包含目标服务器不支持的功能，落地前必须核对安装版本。

补充决策见[五台服务器的方案收敛](五台服务器的方案收敛.md)。上述版本由用户提供；未连接服务器验证。保护范围覆盖 CPU、内存、磁盘容量/inode 与磁盘 I/O，服务优先级逐机确定。

第二轮复核见[Anysearch 复核与新增发现](Anysearch复核与新增发现.md)。复核保留总体方向，但收紧 Monit 的 Docker 适配范围，并补充 API 兼容性、内存参数语义与磁盘存储路径。

## 1. 对任务的理解

已知环境是 Ubuntu，会部署大量 Docker 容器。用户确认以避免整机崩溃为优先目标，允许重启和直接终止进程；“闲置资源”暂按“限制资源”理解。该授权明确了自动化方向，具体服务优先级仍需登记。

已知背景是服务器经常出现资源占满、影响生产的情况。目标是尽早识别危险、定位可处置对象、及时缓解，并留下能够复盘的证据。

真正需要交付的能力包括：

1. **发现**：采集主机和工作负载的资源、压力及健康状态。
2. **判断**：区分正常高负载、短时突发和持续恶化，判断是否需要干预。
3. **定位**：关联到服务、容器或任务，结合业务优先级选择对象。
4. **处置**：限制资源、降低任务并发、停止接单、清理已授权的临时数据，必要时停止工作负载。
5. **验证**：确认资源压力和业务健康是否恢复；失败时升级告警，避免无限重试。

当前“资源占满导致宕机”是用户描述，还不能直接等同于内存 OOM。需要确认是主机重启、SSH 无响应、应用超时、磁盘写入失败，还是个别进程退出。硬件故障、内核故障等也可能表现为不可用，单个守护服务无法覆盖所有原因。

## 2. 第一轮结论

**已有成熟组件覆盖大部分基础能力，建议先组合验证，再决定是否自研。**

- 单机、少量固定服务：优先对比 **Monit + systemd 资源限制**，能够较快验证规则处置。
- Linux 内存压力是主要故障：优先评估 **cgroup v2 + systemd-oomd**；旧环境可将 **earlyoom** 列为候选。
- 已有 Prometheus 或 Zabbix：复用采集、告警与历史数据，补本地保护与受控动作执行。
- 已有 Kubernetes：先检查资源配置、系统预留和节点压力驱逐，避免再建一套独立的宿主机杀进程逻辑。
- 业务存在复杂优先级、任务暂停/恢复、处置审计或多控制器协调：再开发轻量策略执行服务。

这是基于下面能力对比作出的工程判断，尚不是对生产环境的最终推荐。没有发现能在不了解业务重要性的情况下，安全自动解决所有资源危机的通用产品。

### 针对已确认的 Ubuntu + Docker 环境

当前首选验证组合是 **Docker 原生资源预算与日志治理 + 主机/容器联合监控 + 本地容器处置**。Monit 可承载简单固定规则，但 Docker 自动发现、资源聚合和动作身份核验需要脚本/API 适配；systemd-oomd 是内存问题明确后的补充候选，不应因系统是 Ubuntu 就直接启用。

1. **先盘点现有容器配置**：内存/CPU/PID 限制、日志驱动与轮转、重启策略、数据卷、服务负责人。未配置资源限制的容器是重点核查项，但不能据此认定它就是事故根因。
2. **主机与容器同时观测**：主机看可用资源和压力，容器看 CPU、内存、I/O、任务数及退出事件。临时调查可用 Docker stats/API，长期采集可评估 cAdvisor + node_exporter，并接入已有监控。cAdvisor 提供容器用量和性能指标，不负责自动处置。[Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/)、[cAdvisor](https://github.com/google/cadvisor)
3. **统一指标口径**：Linux 的 Docker CLI 内存显示扣除了部分缓存，而 API 返回原始用量及缓存信息。不能直接比较不同口径的数字，再据此判定泄漏；容器限额和主机总量也要分别判断。[Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/)
4. **优先使用容器管理接口**：已授权处置的对象按容器 ID 及业务身份核验，先减载或限额，再 stop，必要时强制终止。Docker stop 默认先向主进程发送停止信号（通常为 SIGTERM），超时后 SIGKILL；应用是否正确处理信号需要测试。动态 update 的支持项和降低内存限额后的影响也需验证。[Docker stop](https://docs.docker.com/reference/cli/docker/container/stop/)、[Docker update](https://docs.docker.com/reference/cli/docker/container/update/)
5. **与重启策略协调**：手动停止后 Docker 的重启策略会暂时不再自动拉起，恢复条件取决于策略及 daemon/人工操作。直接杀宿主机 PID 与显式停止容器的结果不能等同；还需确认是否有 Compose 外部管理器、Swarm 或其他控制器重新创建容器。[Docker restart policy](https://docs.docker.com/engine/containers/start-containers-automatically/)

建议将保护进程作为宿主机 systemd 服务评估，便于在 Docker daemon 不响应时仍读取主机压力；这并不保证 Docker API 动作还能成功。PoC 需验证 daemon 超时后的升级路径与内核资源限制兜底，不把任意宿主机 PID 强杀作为默认后备逻辑。

执行器需要 Docker 管理权限，但管理 socket 是高权限入口，应收敛到受控本地执行器，避免暴露给任意远端调用。[Docker 安全说明](https://docs.docker.com/engine/security/)

如果这些服务器通过 Compose 管理，资源配置还应回写到正式部署定义，并在重建后核验有效值；仅修改运行中的容器不能保证下次部署仍保留。这里尚未确认是否使用 Compose。

## 3. 成熟方案对比

“成熟”在本调研中指有明确上游、文档和可复用实现，不代表已通过本公司生产验证。部署成本是相对判断；版本维护、软件许可和公司软件源适配还需要在候选收敛后核验。

| 方案 | 能做什么 | 自动处置能力与边界 | 本任务中的位置 |
| --- | --- | --- | --- |
| Prometheus + node_exporter + Alertmanager；按需接 Grafana | 主机指标、规则告警、历史查询和展示 | Alertmanager 负责通知、聚合和路由；Webhook 还需要接收端实现实际动作 | 已有平台时优先复用；不单独承担紧急保护 [S1–S3] |
| process-exporter | 从 `/proc` 采集选定进程并按规则分组 | 提供定位线索，不负责资源隔离或终止 | 补主机监控缺少的进程归属信息 [S4] |
| Monit | 本地监控进程、系统资源和服务状态 | 规则可触发 alert、restart、stop、exec；需明确目标和动作 | 固定服务规则框架；Docker 需额外适配且核对安装版本 [S5] |
| systemd + cgroup v2 | 按服务或服务组限制资源 | 内核持续执行限制；不是完整告警平台 | Linux 环境下的基础保护层 [S6–S7] |
| systemd-oomd | 基于内存压力及 swap 条件提前处理 OOM 风险 | 选择符合条件的 cgroup，并向其中全部进程发送 SIGKILL | 专用内存紧急保护，必须验证 cgroup 划分 [S8] |
| earlyoom | 检查可用内存、空闲 swap 并选择进程 | 按条件发送 SIGTERM/SIGKILL，支持候选偏好、排除与 dry-run | 简单内存保护备选，不能替代业务优先级策略 [S9] |
| Meta oomd | 可配置检测器和动作插件的用户态 OOM 管理 | 适合定制内存策略；与 systemd-oomd 是不同项目 | 有复杂内存策略时再深入，首轮集成成本较高 [S10] |
| Zabbix | 集中监控、触发器和动作 | 支持远程命令；Agent/Proxy 默认禁用远程命令，需显式配置 | 公司已有 Zabbix 时优先评估复用 [S11] |
| Netdata | 节点观测与告警 | 告警状态变化可执行自定义脚本；业务处置逻辑仍需设计 | 观测与快速排障候选 [S12] |
| Docker 原生资源限制 | 容器 CPU、内存等约束 | 默认没有资源限制，需要明确配置；不提供完整的业务处置闭环 | 容器场景先补资源预算 [S13] |
| Kubernetes 原生机制 | 工作负载资源管理、节点压力驱逐、系统资源预留 | kubelet 可先回收资源再驱逐 Pod；恢复依赖控制器及可用容量 | 已有 K8s 时优先沿用原生控制路径 [S14–S15] |

仅为解决这个任务而新引入 Kubernetes，通常会扩大运维范围；这是项目成本判断，不是其能力不足。Windows 场景需要另行评估原生资源控制及服务管理，不能照搬这里的 Linux 配置。

## 4. 关键技术及容易误解的地方

### 4.1 监控告警和本地保护分别承担什么

node_exporter 暴露主机指标，包含受支持环境下的 PSI 压力指标；进程级归属可补 process-exporter。Prometheus 计算告警，Alertmanager 再分组、抑制和发送通知。Webhook 是对外事件接口，不是已经实现的安全执行器。[node_exporter][S1]、[告警架构][S2]、[Webhook 配置][S3]、[进程采集][S4]

**项目建议**：中心平台负责可观测性和管理，本地保护不依赖网络往返。告警链路的采样、计算和分组等待都需要纳入响应时延；内存突然暴涨时，不能假定中心通知到达前主机一定还能工作。

### 4.2 cgroup v2：给工作负载划定资源边界

cgroup 把一组进程作为资源管理对象。`memory.high` 施加回收压力与节流，本身不会触发 OOM kill；`memory.max` 是内存硬上限，无法回收到限额内时可能发生组内 OOM。`cpu.max`、`io.max`、`pids.max` 分别可用于 CPU 配额、块设备 I/O 限速和任务数限制。[Linux cgroup v2][S7]

systemd 提供相应配置入口，例如 `MemoryHigh`、`MemoryMax`、`CPUQuota`、`TasksMax`。注意 `CPUQuota=100%` 表示一个 CPU 核的时间配额；具体指令支持要核对 systemd 和内核版本。[systemd 资源控制][S6]

**项目建议**：先为业务分组，再按峰值、业务时延和系统余量设置预算。每个服务都有单独上限也不意味着主机总量安全，仍需核算并发峰值与内核、SSH、监控等开销。I/O 限速不限制磁盘已占用容量；磁盘空间需要另外治理。动态压低内存限额可能直接造成强回收或 OOM，不应作为通用无损动作。

补充：Docker `--memory-reservation` 不能当作 `memory.high`；OpenContainers cgroup v2 实现将 reservation 写入 `memory.low`。另需核对容器 swap 总预算与实际运行时版本，见[第二轮内存语义复核](Anysearch复核与新增发现.md)。

### 4.3 PSI：资源争用已经造成多少阻塞

PSI（Pressure Stall Information）记录任务因 CPU、内存、I/O 不足而停顿的时间比例，可从 `/proc/pressure/` 读取，也支持 cgroup 级观测和阈值事件。`some` 表示有任务因资源等待，`full` 表示所有非空闲任务同时等待；系统级 CPU `full` 不适合按同样含义解读。[Linux PSI][S16]

**项目建议**：将 PSI 与可用容量、增长速度、应用健康结合。PSI 是压力信号，不是预测所有故障的算法；突发分配可能在平滑指标明显升高前就耗尽内存。节点 PSI 也不能直接指出哪个进程应被终止。

### 4.4 systemd-oomd 和 earlyoom 如何选择

systemd-oomd 依赖 systemd、完整 cgroup v2 层级、内存记账及 PSI。上游建议启用 swap 以留出反应时间，无 swap 仍可使用压力动作，但需要额外调优。它选择符合条件的后代 cgroup，终止粒度不是随意挑一个 PID；多个业务混在同一组会扩大影响。[systemd-oomd][S8]

earlyoom 路径更简单：根据可用内存和空闲 swap 阈值，默认结合 `oom_score` 选择对象。其 `--avoid` 是降低被选择倾向，不能当作绝对保护名单；排除需求应核对 `--ignore` 等选项及实际版本。内存阈值、无 swap 行为、信号处理也需要测试。[earlyoom][S9]

**项目建议**：内存紧急终止机制先选一个主责实现，避免 earlyoom、systemd-oomd、自研程序同时选择牺牲对象。若与内核 OOM、容器控制器共存，需要明确职责和验证先后行为；不能要求内核永不介入。

### 4.5 Kubernetes 要沿着现有控制器处置

kubelet 的节点压力驱逐可应对内存、磁盘及 PID 压力；与 API 发起的自愿驱逐不同，节点压力驱逐不受 PodDisruptionBudget 的同样保护，硬阈值可能立即终止。系统与 Kubernetes 守护进程需要单独资源预留。[节点压力驱逐][S14]、[系统资源预留][S15]

**项目建议**：先检查 requests/limits、节点预留、驱逐阈值和业务优先级；不要让宿主机工具绕过编排器随机杀容器进程。自动重建 Pod 也不等于业务恢复，还需要其他节点容量、数据恢复条件和健康检查。

## 5. 按资源类型制定处置策略

下面是待 PoC 验证的设计建议，不是成熟工具默认行为，也不是已批准的生产策略。

| 风险 | 需要一起观察 | 优先缓解动作 | 需要避免 |
| --- | --- | --- | --- |
| 内存耗尽 | MemAvailable、swap 活动、memory PSI、cgroup 用量/事件、业务延迟 | 停止接收非关键任务、降低并发；必要时停止已允许的低优先级工作负载 | 仅凭 used 百分比杀进程；把暂停当作释放内存 |
| CPU 饱和 | CPU 使用、运行队列、CPU PSI、业务延迟、虚拟机 steal | 降低后台并发、调整 CPU 权重/配额、限流 | CPU 一到 90% 就重启；忽略限速使任务积压更严重 |
| 磁盘容量或 inode 耗尽 | 每个挂载点剩余字节、inode、增长速度、写入来源 | 日志轮转与保留策略；清理明确可删除的临时文件；停止异常写入方 | 无差别删除大文件、数据库文件或容器卷 |
| 磁盘 I/O 拥塞 | I/O PSI、设备延迟、队列、工作负载 I/O、业务健康 | 限制后台 I/O、降低并发、暂停批任务 | 将 iowait 或设备利用率单独当作杀进程依据 |
| 进程/线程或 FD 耗尽 | cgroup 任务数、线程增长、进程 FD、错误日志 | 配额、防止无限创建、停止已确认失控的工作负载 | 仅看 CPU/内存；在紧急时大量 fork 外部诊断命令 |

磁盘治理应区分日志所有者：宿主机或应用自管文件可用 logrotate，Docker 管理的 stdout/stderr 日志优先用日志驱动自身轮转，不直接交给外部 logrotate 修改。logrotate 的 `copytruncate` 存在复制与截断间的丢日志窗口；Docker 默认 `json-file` 日志若未配置轮转，可能耗尽磁盘。改 Docker 默认日志设置通常不会自动改变已有容器的日志配置。[logrotate][S17]、[Docker 日志][S18]

Docker 29 使用 containerd image store 时，还需检查实际 containerd 数据目录及其挂载点；构建缓存可评估 BuildKit GC，日志背压需评估阻塞与丢日志取舍，见[第二轮磁盘治理补充](Anysearch复核与新增发现.md)。

文件删除后若仍被进程打开，空间不一定立即释放；实施清理后必须重新确认剩余空间，必要时按服务流程重新打开日志。内存风险下暂停进程通常保留其内存；I/O 阻塞也可能使终止和资源释放不能马上完成。因此“命令成功返回”和“危险解除”必须分开记录。

网络带宽、连接数、GPU 显存是否纳入一期，取决于事故证据。GPU 显存与主机内存不是同一指标，不能直接套用 OOM 工具。

## 6. 建议的组合架构

此处是本项目候选设计，环境确认后可以删减，未要求把所有组件一起部署。

```text
主机 / 服务 / 容器指标 ──→ 中心监控、历史查询与告警
          │                          ↑
          ↓                          │ 处置记录与结果
本地压力判断 → 目标与权限校验 → 动作执行 → 再次检查
          ↑                     │
          └──── 冷却、恢复、失败升级 ──┘

基础层：按工作负载划分资源预算，给主机基础服务保留余量
紧急层：按环境选择内存兜底机制，并与上层处置协调
```

### 本地策略至少包含的约束

- **准确识别目标**：优先用 systemd unit、容器身份或调度器任务身份；若操作 PID，需要验证启动时间等身份信息，防止 PID 复用。
- **限定可操作对象**：关键服务保护清单优先；未知业务默认只告警。不要从进程名或占用排名推断业务价值。
- **连续观测与紧急分支**：普通风险需要持续窗口及恢复滞回；临近耗尽可走预先批准的紧急规则，不能一律等待长窗口。
- **分级动作**：先业务减载或限流，随后优雅停止；只对允许对象在超时后升级强制终止。systemd-oomd 的 SIGKILL 路径应单独理解。
- **幂等和冷却**：同一目标同一时间只有一个动作；控制重试次数和重启频率，避免监督器马上拉起失控服务。
- **执行后验证**：同时检查资源压力、业务健康和预期容量；无改善时升级告警，不能不断杀更多进程。
- **可停用、可回退**：保存原配置，支持关闭自动动作与撤销可逆限额。杀进程、删除数据不可真正回滚，恢复流程需业务方确认。
- **自身可生存**：限制采集开销与日志体积，为守护程序预留资源；中心断网或磁盘满时仍要尽可能保留最小处置记录。
- **权限收敛**：采集与高权限动作可分离；执行器只允许已登记动作，不能把 Webhook 文本直接当 shell 命令。

### “提前发现”如何实现

一期采用阈值、趋势和压力组合，不需要先引入机器学习。容量类风险可估算：

`预计触及安全余量的时间 ≈ (当前可用容量 − 安全余量) / 近期正增长速率`

这只是局部线性近似，适合辅助预警；对突发分配、可回收缓存和周期波动可能失真。内存是否危险还要结合压力，不能把该估算直接变成自动终止指令。

## 7. 复用还是自研

| 条件 | 建议 |
| --- | --- |
| 目标只是几个固定服务超阈值后执行固定动作 | 先验证 Monit；Docker 场景把脚本适配成本纳入对比 |
| 主要是 Linux 内存危机，服务已合理分组 | 先验证资源预算和 systemd-oomd |
| 已有 Zabbix，动作流程较简单 | 验证原生动作与最小权限命令集 |
| 已有 Prometheus，需要快速本地保护 | 保留监控平台，补本地执行；不依赖告警 Webhook 作为唯一紧急入口 |
| 需要业务级优先级、跨资源判断、任务恢复与完整审计 | 自研薄策略层，调用已有服务管理/编排接口 |
| 环境未知、事故原因未知 | 收集事实与只读观测，暂不定语言和终止算法 |

如果最终需要编码，可以按团队经验选择 Go 或 Python；目前没有证据支持先定某种语言。自研的价值应集中在公司的业务规则，而不是重新实现资源隔离、指标存储或 OOM 算法。

## 8. 建议推进顺序

1. 取得环境清单、服务重要性列表，以及至少一次事故时间线。
2. 在隔离测试机验证资源隔离和一个成熟候选工具，记录其对正常峰值的影响。
3. 以只记录不执行的方式观察候选动作，覆盖业务高峰和批任务周期。
4. 仅对一个明确可恢复的低优先级工作负载开放自动动作。
5. 根据误判、恢复时间与组件开销决定是否扩展或自研。

具体问题与验收项目见[需求确认与验证计划](需求确认与验证计划.md)。调研到此尚未完成生产环境验证、性能测试或兼容性测试，也没有给生产服务器配置任何自动终止规则。
