# Leader 最新汇报后的测试交接

更新时间：2026-09-18

用途：记录 leader 最新反馈、两层技术范围和下一步测试入口。本文档是项目交接依据，不依赖某一次会话记忆；本地 EXP-001～EXP-006 完成后，下一步转入 Guardian 最小风险检测与自动处置设计。

## 1. 最新结论

本次向 leader 汇报后，工作分成两个层次；本地 PoC 已完成，当前重点是把“发现宕机风险并自动处理”落实为 Guardian 的最小闭环：

### 第一层：救援能力保障

目标不是保证服务器永不宕机，而是资源高压时，管理员仍有机会进入服务器并完成必要操作：

```text
新建 SSH 连接 → 执行诊断命令 → 停止测试中的异常任务
```

优先验证现成机制：

- 验证 Linux、systemd/cgroup 和 Docker 隔离对救援链路的影响；资源边界只在业务明确允许时作为可选防线。
- CPU 竞争时比较 CPU 权重、CPU 配额等方式对 SSH 和救援操作的影响。
- 内存场景单独验证，因为提高 CPU 优先级不能解决内存不足；内存上限、内存保护等配置只作为测试对照，不作为所有业务的默认要求。
- 不因为“开发一个常驻救援程序”就认为它天然拥有资源。专用程序仍需被纳入资源保护和压力测试。

验收重点：高压场景下，SSH、登录后的 shell、诊断命令和停止测试任务的链路仍可用。

### 第二层：自动风险处置

目标是没有人及时操作时，系统按明确规则完成受控止损：

```text
观测 → 定位 → 判断是否允许处理 → 执行动作 → 验证恢复
```

优先评估现成策略和本地处置管道，再定义 Guardian 的最小实现：

- systemd-oomd 等工具主要用于评估内存危机下的自动选择和终止行为。
- systemd/cgroup、Docker 的 CPU/内存限制属于持续执行的事前约束，不等同于危机发生后的智能处置。
- Monit 等工具适合对已知服务按固定规则检查和执行动作。
- 如果必须按“近期资源增长 + 业务保护名单 + 允许动作”选择对象，就由 Guardian 补充实时检测、对象定位、策略判断、分级动作和恢复验证。

自动处置涉及终止或重启风险。没有测试机、保护名单、允许动作和明确授权前，保持自动变更关闭，只做观测、模拟和受控测试。

## 2. 测试顺序

### 2.1 第一层测试：先证明人还能救援

1. 选择非生产 Linux 测试机，确认 OS、内核、systemd、cgroup 和 Docker 版本。
2. 准备可丢弃的测试容器或测试进程，记录 SSH、shell、诊断命令和停止命令的基线表现。
3. 分别制造有界 CPU 压力和内存压力，不直接在生产服务器注入故障。
4. 对比无额外限制和业务明确允许的资源隔离配置；不把设置资源上限作为救援能力的统一前提。
5. 记录 SSH 建连时间、命令完成情况、停止任务耗时、压力指标、OOM/cgroup 事件和测试服务自身开销。
6. 若救援链路不稳定，先停止扩大压力，检查保护对象、cgroup 层级和资源预算，不进入自动终止测试。

### 2.2 第二层测试：先验证现成规则，再考虑自研

1. 在同一类非生产环境复用第一层的压力场景。
2. 先以实时、只读方式确认能否发现风险、定位容器/cgroup/进程组，并保存现场快照。
3. 对 systemd-oomd、Monit、Docker API 或其他现成机制逐项记录：触发条件、选择对象、动作类型、保护/排除规则和恢复行为。
4. 未获得明确授权前，不启用真实 SIGKILL、容器重启或资源变更；使用 `observe/simulate`、测试对象和审计记录验证流程。
5. 如果现成规则无法表达业务要求，进入 Goal 4，补充 Guardian 的最小能力，不开发完整监控平台，也不统一配置容器内存限制。

## 3. 当前必须补齐的信息

- 测试机地址、系统版本和故障注入授权人。
- SSH 失效的真实表现：无法建连、认证慢，还是登录后命令无法执行。
- 第一层的资源预算、保护对象和预期救援动作。
- 第二层允许自动处理的测试对象、禁止处理的保护名单、动作分级和动作上限。
- 是否允许测试 systemd-oomd 或 Guardian 的强制终止行为，以及如何恢复测试服务。
- 业务健康检查、结果验证标准和测试停止条件。

这些信息未确认前，不能把 PoC 结果当成生产阈值，也不能承诺兼容所有服务器。
