# 本地人工维护通道验收

更新时间：2026-09-22

本次验收使用独立的本地 disposable Ubuntu 22.04 虚拟机，2 vCPU、4 GiB 内存、20 GiB 磁盘。验收从 macOS 宿主机通过真实 `ssh` 发起；没有使用 Multipass 管理命令作为登录证明，没有连接生产，也没有停止容器。

## 结果

基线、CPU 压力、内存压力、磁盘接近危险和 CPU+内存混合压力均通过。每个压力场景都重新建立了 SSH 连接，并能完成：

- 看到 Guardian 正常、开机启用、只读观察和 Collector 在线；
- 看到 Beszel 隔离实例健康，并访问本地监控页面；
- 使用只读 Docker 查询查看容器；
- 查看 SSH、logind、Docker、containerd、日志和维护 CPU/内存/任务边界；
- 确认 Broker 没有授权标记、没有 socket、没有自动动作；
- 压力结束后恢复正常，磁盘压力文件自动清理。

磁盘场景期间根盘使用率约 92%，维护域仍固定在 CPU 0，压力域固定在 CPU 1；压力域的内存上限为 512 MiB、交换空间上限为 0、任务上限为 256。维护账号的登录会话使用独立的 CPU 0、内存和任务数保护。

## 本次原始结果摘要

以下耗时来自宿主机保存的原始 SSH 输出；时间单位为毫秒。所有场景均为 `PASS`，没有写入 IP、密钥或其他凭据。

| 场景 | 结果 | 新 SSH 诊断耗时 |
| --- | --- | ---: |
| 基线 | PASS | 321 ms |
| CPU 压力 | PASS | 292 ms |
| 内存压力 | PASS | 323 ms |
| 磁盘压力 | PASS | 369 ms |
| CPU + 内存混合压力 | PASS | 362 ms |
| 最终清理确认 | PASS | 414 ms |

磁盘场景的根盘峰值为 92%（20 GiB 磁盘，剩余约 1.7 GiB）；最终清理确认恢复到约 14% 使用率。所有场景均观察到维护域 `EffectiveCPUs=0`、压力域 `EffectiveCPUs=1`，压力域 `MemoryMax=512 MiB`、`TasksMax=256`，维护会话 `AllowedCPUs=0`。最终状态仍为 Guardian healthy、Beszel healthy、自动动作关闭、Broker 标记和 socket 均不存在。

## 这次验收证明什么

它证明当前本地版本在受控的资源竞争边界内，人工可以重新登录、看状态、读 Docker 和确认 Beszel/Guardian。它不证明任意内核、网络、设备或根盘完全耗尽时 SSH 永远可用，也不证明 x86_64 非生产或生产环境可用。

## 运行边界

- 允许处理名单默认为空。
- 自动动作默认关闭，Broker 默认关闭。
- 压力工具只接受固定场景和限时参数，不接受任意命令或任意删除路径。
- 应急空间只允许 Guardian 按自身清单释放；不会自动清理业务文件、容器数据、日志或镜像。
- 没有真实业务健康检查时，系统只能报告“宿主机风险已缓解，业务恢复待人工确认”。
