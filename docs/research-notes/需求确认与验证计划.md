# 需求确认与验证计划

日期：2026-09-16。已确认共 5 台性能有差异的服务器，业务优先级逐机讨论。参考机器为 Ubuntu 22.04.5、systemd 249、cgroup v2、Docker 29.1.3（用户提供）；大量使用 Docker，以及允许重启和终止进程；资源限制暂按用户表述理解。以下列出剩余问题和建议测试，尚未在公司服务器执行。

| 优先级 | 问题 | 为什么影响选型 | 当前状态 |

## 2. 一次事故的最小证据包

请按实际能取得的信息填写，缺失项保持“未知”：

- 事故时间及持续时长、服务器角色与运行的业务。
- 故障表现：SSH、应用健康接口、网络连通、主机是否重启分别是什么状态。
- 故障前后 CPU、MemAvailable、swap、磁盘空间/inode、I/O 与业务延迟趋势。
- 进程、服务或容器用量排行，及其所属任务；用量最大只代表候选线索。
- 内核 OOM、磁盘错误、systemd/容器退出原因和重启记录。
- 当时新增任务、发布变更、流量变化、日志增长等事件。
- 人工最终做了什么，哪一步之后恢复，是否有数据损失或重复执行。

需要尽可能保留故障前的历史数据。重启后仅凭当前 `top` 或 `free` 输出，通常无法证明此前事故根因。收集材料时保留必要字段即可，避免将凭据和完整敏感命令行复制进报告。

## 3. 候选验证路径

### 路径 A：Linux 固定服务（补充路径）

比较“资源限制 + Monit”与“资源限制 + systemd-oomd（内存方向）”。前者验证自定义动作，后者验证内存紧急保护；两者承担的职责不同，不能只比较是否杀掉了进程。

若目标系统不满足 systemd-oomd 条件，再评估 earlyoom 或仅采用资源限制；不要为试工具直接升级生产内核。

### 路径 B：Docker（当前主线） / Kubernetes（条件分支）

Docker：检查容器资源限额、日志轮转和自动重启策略。优先比较 Docker stats/API 与 cAdvisor 的采集方式，并验证容器身份识别、优雅停止、强制终止和防止反复拉起。Kubernetes：检查节点预留、工作负载资源配置和驱逐机制。只有原生机制无法满足业务策略时，再设计补充服务。

### 路径 C：已有集中监控

保留原平台，用已有数据还原事故。验证它是否已支持所需动作，以及中心不可达时的本地保护能力；不以“能发通知”作为已经完成自动保护的验收依据。

## 4. PoC 验证矩阵

Anysearch 复核新增前置检查：Docker Server API 最低版本与客户端兼容性；Monit 安装版本；实际 containerd/runc 版本；Docker/containerd 存储目录和挂载点；有效 memory.low/high/max/swap.max；日志轮转与背压；是否执行本地镜像构建及其缓存 GC。来源和原因见[复核报告](Anysearch复核与新增发现.md)。

所有资源耗尽实验均放在隔离测试环境，使用明确可丢弃的工作负载与有界资源。磁盘实验使用独立测试卷；不填满生产根分区。

| 场景 | 观察内容 | 通过标准 |
| --- | --- | --- |
| 采集器正常响应但容器指标缺失 | 比对容器清单、资源指标和采集错误 | 所有预期容器都有有效数据，不能仅用 endpoint UP 验收 |
| memory reservation 与节流配置 | 对照有效 memory.low/high/max/swap.max 和压力表现 | 不把 reservation 当作 high，预算与实际行为一致 |
| 不同存储后端与日志阻塞 | Docker/containerd 挂载点、缓存 GC、日志投递 | 容量监测无遗漏；日志阻塞或丢失取舍符合约定 |
| 正常业务峰值、缓存增长、短时 CPU 满载 | 是否误报、误限流、误终止 | 测试集中没有未授权动作；正常峰值业务指标在约定范围内 |
| 单个后台任务缓慢泄漏内存 | 预警、目标识别、动作、恢复时间 | 预先允许的对象被准确处置，关键服务继续可用 |
| 内存快速突发增长 | 用户态守护程序是否来得及响应，内核限额是否生效 | 在所测速率下影响受控；记录无法拦截的条件 |
| 多服务同时增长 | 单服务限制外的主机总量压力 | 能观测全局风险，不把每服务未越限当成全机安全 |
| CPU / I/O 持续竞争 | 限流后的关键业务延迟和任务积压 | 关键业务改善，后台积压没有引入更严重问题 |
| 日志填满测试卷或 inode 耗尽 | 定位、清理范围、空间实际释放 | 只操作允许目录；释放与业务恢复被分别确认 |
| 目标退出、PID 复用、子进程仍存活 | 动作身份核验、服务组边界 | 不操作新进程或无关工作负载 |
| 动作超时、权限不足、进程无法及时退出 | 重试与升级路径 | 无无限循环，有明确失败事件和人工接管入口 |
| 服务自动拉起且再次超限 | systemd、容器或其他控制器的交互 | 没有重启风暴；达到重试预算后停止自动重试并告警 |
| Docker daemon 无响应、容器重建、部署配置覆盖 | API 超时、对象身份变化、限额持久性 | 不误操作替代容器；超时可升级；重建后有效配置符合预期 |
| 中心监控断网、本地磁盘满 | 本地判断和最小审计能力 | 已批准的本地保护不依赖中心；数据丢失范围可解释 |
| 守护程序自身异常或被重启 | 自身资源开销、状态恢复、重复动作 | 重启后不重复危险动作；没有明显挤占业务资源 |
| 停用自动化与撤销限额 | 回退流程与恢复检查 | 可恢复到已记录配置；不可逆动作有明确恢复流程 |

## 5. 指标与验收口径

以下目标值需要结合业务基线商定，不预设“CPU 90% 就杀”一类统一生产阈值。

| 指标 | 测量方法 | 目标 |
| --- | --- | --- |
| 发现时延 | 风险首次满足定义到被识别的时间 | 待确认 |
| 动作时延 | 识别到执行器实际开始动作的时间 | 待确认 |
| 缓解时间 | 动作开始到资源持续回到安全范围 | 待确认 |
| 业务恢复时间 | 风险发生到健康检查、延迟/错误率恢复 | 待确认 |
| 误处置 | 正常场景中不必要或对象错误的动作 | 测试集禁止出现未授权动作；观测数量同时记录 |
| 漏检 | 已满足风险定义但未触发的事件 | 待确认，并逐个解释 |
| 运行开销 | 正常与压力下守护组件 CPU、RSS、I/O、日志增长 | 待确认 |
| 可解释性 | 触发指标、规则版本、目标、动作、结果是否齐全 | 每次自动动作均可追溯 |

可以从秒级本地观测开始测试，但采样周期不是响应保证；窗口、调度延迟、动作耗时都必须测量。窗口和阈值应根据正常峰值及事故重放校准。

## 6. 阶段交付物

1. **需求确认**：环境清单、事故分类、业务保护名单与动作授权表。
2. **候选验证**：一到两个候选的版本、配置、实验记录、开销和失败边界。
3. **选型决策**：选择理由、淘汰理由、剩余风险、运维成本及是否需要自研。
4. **有限试点**：先只记录，再对允许的低优先级服务开放动作，并验证停用流程。

本轮已完成的是技术调研文档与上述验证计划；候选部署、事故复现、性能结论和生产试点均未完成。
