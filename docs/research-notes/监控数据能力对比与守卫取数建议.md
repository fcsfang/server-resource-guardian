# 监控数据能力对比与守卫取数建议

调研日期：2026-09-17。针对五台 Ubuntu / Docker 服务器，参考环境为 Ubuntu 22.04.5、systemd 249、cgroup v2、Docker 29.1.3。通过 Anysearch 检索和读取官方资料；本文是文档能力核对与工程建议，不是部署实测或性能排名。

## 1. 结论

监控系统的价值不仅是把本机读数传给另一个程序，还包括现成采集器、持续保存历史、计算变化率和聚合、汇集其他机器及应用的数据。只需少量本机当前数据时，直接读取 Linux / Docker 通常更合适；需要大量现成指标时，可以复用本机采集器，不必经过远端中心。

对当前需求，保留已有 Beszel 作为集中监控是合理候选，本机紧急保护不必依赖 Beszel Hub。若希望减少本机详细指标采集开发，Netdata Agent 或 node_exporter / cAdvisor 值得试验；这不要求立即替换集中平台。需要统一计算多个业务和多台机器的指标时，再评估 Prometheus；已有 Zabbix 时优先复用其模板、历史和事件能力。

## 2. 统一任务下比较

比较任务：读取资源状态、判断近期变化、查到容器候选，为自动保护提供证据。采集项可用性取决于具体版本、权限、内核、存储及启用配置。下面的“需要补”是相对于这个任务，不是说其他平台无需配置维护。

| 选择 | 现成数据与取数方式 | 对守卫最有价值的部分 | 相对不足或新增工作 |
| --- | --- | --- | --- |
| Beszel | 主机 CPU、内存、磁盘空间和 I/O、网络、负载等；容器 CPU、内存、网络历史；Hub 的 PocketBase REST API | 已有部署即可复用历史与多机数据，适合基础资源变化查询 | 官方 API 明示小版本可能改变返回结构；未确认其具有等同 PromQL 的通用统计查询能力；PSI、容器限流/内存事件等需逐项核对，不能假定齐全；Hub 断连会影响查询 |
| Prometheus + node_exporter + cAdvisor | node_exporter 提供主机内存、磁盘、文件描述符、PSI 等；cAdvisor 提供容器用量、CPU 限流计数/时长、内存分类等；Prometheus HTTP API 查询时间序列和表达式结果 | 可以按主机/容器筛选、排序、求变化率、聚合，并组合应用提供的业务指标 | 需要部署和配置采集器、采集目标及指标标签；不是装上 Prometheus 就自动有全部指标；大量标签和高频采集带来容量成本；完整历史查询依赖 Prometheus 服务 |
| Zabbix + Agent 2 + Docker 模板 | 官方模板提供容器自动发现、统计、CPU 限流、进程数、网络、状态及 Docker 配置等；集中 API 提供历史查询等能力 | 资源数据与主机、监控项、触发事件组织在同一系统中，适合已有 Zabbix 的环境 | 程序需要对应 host/item 标识和数据类型；采集间隔、预处理和保存策略影响可见数据；模板列出的字段不能保证在所有 cgroup / Docker 版本都存在 |
| Netdata Agent | 本机采集主机、cgroup、容器及 systemd 服务指标；Agent REST API 直接提供节点指标、告警等；具有本地历史能力 | 守卫可访问本机 Agent，复用详细采集和近期历史，不必绕中心；适合细看资源短时变化 | 仍有一个本机组件依赖；需限制不需要的采集和存储开销，理解 chart/context/dimension 等字段；高频采集不保证高压下无延迟，也不等于自动处置可靠 |
| Monit（不含 M/Monit） | 按配置检查进程、系统资源、文件系统、端口/协议和程序退出状态；可将检查结果直接接入本机动作 | 对固定服务，如“进程不存在或检查持续失败后重启”，可以少写一段检查与动作衔接代码 | 不适合作为动态 Docker 全量指标与长期历史查询平台的替代；复杂容器选择仍需补充。M/Monit 是另一个集中管理产品，不把它的能力算进单独 Monit |

Grafana 通常承担展示与数据源查询界面，本次将数据能力归于 Prometheus 等实际数据源，不将 Grafana 单独视作 Linux/Docker 采集器。

## 3. 用具体问题理解差异

### 问题一：现在本机内存还剩多少？

Linux 当前读数就能回答。仅为这个问题请求远端平台通常收益不大。现成平台读数可能较旧，必须带时间检查。可用内存、已用内存、容器 RSS、缓存和 working set 是不同口径，不可混为同一值。

### 问题二：哪个容器最近十分钟持续增长？

需要连续记录，而不只是一次 docker stats。Beszel 可提供已保存的容器历史供程序分析；Prometheus 可用表达式计算趋势并筛选容器；Netdata 可复用本地保留的时间序列；Zabbix 可查询已配置监控项的历史。若仅需短期变化，守卫也可以自行保留有限采样窗口。

历史中的聚合值不能当成当前瞬时值。接口请求间隔缩短不等于采集频率变高。不能通过更频繁地查询同一条旧记录获得新信息。

### 问题三：容器 CPU 不算高，为什么任务还是很慢？

只看 CPU 使用百分比可能不够，还需要 CPU 配额、限流次数/时间、资源等待和业务状态。cAdvisor 指标文档和 Zabbix Docker 模板明确列出 CPU 限流数据；Netdata 提供 cgroup 监控与资源限制相关能力。Beszel 的基础指标说明不能直接证明这些细项齐全，应核对实际版本。限流也只是线索，不能直接认定慢的根因。

### 问题四：CPU 忙时，是否已经影响在线请求？

需要应用请求耗时、错误率或任务积压。它们不是内核自动知道的内容。Prometheus 可接入应用暴露的指标并计算；Zabbix 可配置相应采集/检查，Netdata 可通过合适的集成采集。任何平台都不能凭空得到公司自定义的订单失败率或业务重要性。仅需一个关键接口健康检查时，守卫直接检查即可，不必因此更换平台。

### 问题五：是否可以停止这个容器？

所有选择都需要公司的业务授权、优先级和允许动作。监控历史不能替代授权。执行前用 Docker 当前身份及状态复核，避免容器重建后处理错目标。

## 4. 取数位置与可靠性

| 路径 | 适用场景 | 需要处理的代价 |
| --- | --- | --- |
| Linux / Docker → 守卫 | 少量明确的本机指标、紧急检查、执行前复核 | 自己维护读取、单位换算、短期采样及错误处理 |
| Linux / Docker → 本机采集器 → 守卫 | 需要较多现成指标，复用 Netdata、node_exporter、cAdvisor 等 | 采集器进程、接口和采样时效依赖；node_exporter / cAdvisor 的指标端点不等于完整长期历史库 |
| 采集器 → 集中平台 → 守卫 | 长期历史、多机信息、统一表达式和业务指标计算 | 网络、中心可用性、鉴权、版本和数据延迟；中心可本机部署，不能将“集中平台”一概当成物理远端 |

推荐把集中平台作为历史与分析来源，把本机复核和必要紧急检测保留在本地。既不要求重写所有采集器，也不要求每个保护动作都绕中心。

## 5. 当前环境的选择建议与验证

1. 已有 Beszel 且第一版只需内存/CPU等少量指标：先验证直接取本机数据的保护程序，Beszel 提供集中查看与复盘。
2. 守卫开始需要大量细项和短期历史：试验本机 Netdata Agent，比较其开销与节约的采集代码；也可按需复用 node_exporter / cAdvisor，不必一次安装所有工具。
3. 需要诸如“哪些机器内存持续增长，同时关键接口错误率上升”的统一查询：评估 Prometheus 指标体系。指标口径和标签关联需要设计，不自动等于因果分析。
4. 公司已有 Zabbix：先盘点 Docker 模板与采集项，无需因为 Beszel 轻量就迁移。
5. 只看护几个固定服务：Monit 可以直接完成合适的检查和动作，不必强制先给自研程序喂数据。

试点应在同一台机器、同一负载下比较：指标是否齐全；相对本机实际状态的数据年龄；容器重建后的身份对应；中心断连、本机采集器退出、Docker超时时的行为；采集与查询的 CPU/内存/磁盘开销。验证主机与容器内存、PSI、CPU限流、磁盘空间/inode和I/O时，逐一明确单位、时间窗口与缺失值，缺失不能当零。

Zabbix 当前 Docker 集成页面展示的模板测试版本为 Docker 23.0.3；这既不是 Docker29 已验证兼容的证据，也不是不兼容的证明。node_exporter、cAdvisor、Netdata同样需在目标版本和挂载/权限设置下验证。

Netdata 官方宣传秒级采集，但各采集器设置和新容器发现周期不同；不能承诺所有指标一秒内更新。其官方横向性能宣传未作为本报告的实测排名依据。Prometheus / Zabbix 的采集频率可配置，不武断声称它们只能十几秒或一分钟采一次。

## 6. 官方来源与证据边界

## 7. v1.3 第5页：按定位需要的信息比较

本轮限定修改第5页及配套讲稿、预览与规格。四列分别比较当前容器用量、历史增长、资源压力、业务影响，不把产品按信息层次强行排等级。Monit保留在第9页固定服务检查与动作部分。

| 工具组合 | 谁占得多 | 谁持续增长 | 资源真的紧张 | 业务受影响 |
| --- | --- | --- | --- | --- |
| Beszel | 有基础容器用量 | 有历史；本方案补增长判断 | 官方基础指标未确认PSI/限流齐全，需核对或补采 | 需另接业务信息 |
| Prometheus + node_exporter/cAdvisor | 由容器采集器提供 | 编写表达式，返回变化或排序结果 | node_exporter提供主机PSI，cAdvisor列有容器CPU限流 | 应用暴露指标，再配置采集 |
| Zabbix + Agent 2 / Docker模板 | 模板提供用量 | 有历史；可配置计算项求变化 | 模板列有CPU限流；PSI另核对或补采 | 接应用数据或配置接口检查 |
| Netdata Agent | 本机容器采集 | 有本机历史和聚合；本方案另实现按增长筛选 | 官方容器指标列有PSI和CPU限流，实机仍需验证 | 启用应用集成或接入应用指标 |

选择依据：已有信息够用优先复用；需要本机压力细项和近期历史时试验Netdata；需要灵活查询计算时评估Prometheus；已有Zabbix先核模板和计算项。多种工具都满足信息需求时，再按取数位置和接入工作量选。上述属于工程建议，不是性能排名。未确认不等于不支持；本方案补实现不等于产品没有任何扩展能力。主机PSI不直接证明某容器是根因；接口探测也不等同于真实用户请求耗时。
