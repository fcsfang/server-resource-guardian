## 1. 核心结论

**这个任务已有较成熟的基础技术可以复用，合理方向是把资源预防、监控、自动处置和恢复验证组合起来，再根据业务需要决定定制开发范围。**

当前建议采用以下原则，最终产品选择由组长结合团队基础和验证结果决定：

1. **先设置资源边界**：通过 Docker、systemd/cgroup 等机制约束工作负载，减少单个任务拖垮整机的可能。
2. **同时看主机和容器**：主机指标判断整体危险，容器及业务信息帮助定位处置对象。
3. **按资源类型采取动作**：CPU、内存、磁盘容量和磁盘 I/O 的风险不同，不能统一用“超过某百分比就杀进程”。
4. **每台机器具有本地保护能力**：集中平台负责观测与管理，紧急保护应尽量不依赖中心网络往返。
5. **统一实现、逐机配置**：五台机器分别定义资源预算、业务优先级和允许动作。
6. **先复用，再补缺口**：既比较 Monit、Zabbix 等成熟工具，也比较现有自动化平台和轻量定制执行器。

上述是基于已查证能力形成的**工程建议**。当前材料足以讨论“选择哪些方案做 PoC（概念验证）”，不足以证明某个组合已经适合生产。

## 2. 背景、目标与已知条件

### 2.1 任务背景

公司服务器曾出现资源占用过高、影响生产的情况，希望新增保护能力，及时发现危险并限制影响，必要时重启服务或终止进程。

当前尚不知道具体事故是主机重启、SSH 无响应、应用超时、OOM 杀进程还是磁盘写入失败。因此本报告覆盖多种资源风险，但不将其中任何一种描述为已经确认的事故根因。

### 2.2 已知环境与未知项

| 项目 | 当前情况 |
| --- | --- |
| 服务器数量 | 5 台，性能存在差异 |
| 工作负载 | 大量使用 Docker；是否使用 Compose、Swarm 或 Kubernetes 未确认 |
| 参考服务器 | Ubuntu 22.04.5、systemd 249、cgroup v2、Docker 29.1.3 |
| 自动处置方向 | 允许重启服务及终止进程；此前“闲置资源”暂按“限制资源”理解 |
| 业务优先级 | 需要逐机与业务方讨论，尚无名单 |
| 一期讨论范围 | CPU、内存、磁盘空间/inode、磁盘 I/O；补充进程/线程与文件描述符风险 |
| 仍需确认 | 内核、硬件规格、swap、存储后端、现有监控、运行时版本、事故证据和恢复要求 |

环境信息由用户提供，尚未连接机器核验；不能推定其余四台版本相同。文件清理和整机重启属于需另行明确的动作范围。

### 2.3 成功应当如何定义

目标是**在资源竞争或耗尽时，尽量保持主机基础能力和关键业务可用，并缩短故障持续时间**。应能完成：发现风险 → 定位对象 → 执行动作 → 检查恢复 → 留存证据。

判断成功时，既看资源是否回到安全范围，也看关键业务是否恢复。进程退出、命令返回成功或监控告警消失，都不能独立证明生产问题已经解决。

## 3. 先理解：为什么不同资源需要不同策略

### 3.1 资源使用率、资源压力与业务健康

三者回答不同的问题：

- **使用率/剩余量**：资源用了多少，还剩多少。
- **压力**：任务是否因为拿不到资源而等待，等待有多严重。
- **业务健康**：请求能否完成，延迟、错误率和任务积压是否正常。

例如 CPU 持续满载可能是正常计算；内存 used 较高可能包含可回收缓存；磁盘容量未满也可能因 I/O 延迟过大而使业务无响应。因此需要组合判断，不能仅看一条百分比曲线。

### 3.2 风险与动作对照

下表为项目策略建议，具体阈值和动作范围需验证。

| 风险 | 重点观察 | 优先考虑的动作 | 容易误判的地方 |
| --- | --- | --- | --- |
| CPU 争用 | 持续占用、CPU 压力、运行队列、业务延迟 | 降后台并发、配额或权重控制、限流 | CPU 高不一定是故障；限速可能加重积压 |
| 内存耗尽 | MemAvailable、内存压力、swap 活动、容器增长、OOM 事件 | 控制新任务、减少并发，必要时停止可牺牲容器 | 暂停通常不释放内存；动态压低硬限额可能触发 OOM |
| 磁盘容量/inode 耗尽 | 每个挂载点剩余空间、inode 和增长速度 | 日志轮转、配额、授权清理、停止异常写入 | 杀进程通常不会清掉已写入的数据 |
| 磁盘 I/O 拥塞 | I/O 压力、设备延迟、队列、容器读写 | 限制后台读写、降低并发 | I/O 限速不解决容量已满，实际效果受存储环境影响 |
| 任务数/FD 耗尽 | 进程线程数、打开文件数、创建失败日志 | 限制增长、定位并停止失控任务 | 只看 CPU/内存可能漏检；大量诊断命令可能进一步耗资源 |

inode 可理解为文件系统用于记录文件等对象的元数据资源；小文件过多时，即使还有磁盘字节空间，也可能无法创建新文件。FD 是进程访问文件、socket 等资源所使用的文件描述符。

网络拥塞、连接表和 GPU 显存保留为扩展分支，待设备和业务需求明确后深入。硬件损坏不属于本报告已经解决的范围。

## 4. 技术体系：哪些能力可以直接复用

### 4.1 事前控制：避免过多任务同时进入

项目建议：如果过载来自同时启动太多批任务，可在入口加入队列、并发槽位和资源预算检查；在线服务可评估限流、背压和降级。这需要业务配合，通用主机 Agent 不一定能直接控制业务入口。

需要跨机分配时，可评估已有调度器。Swarm 的 CPU/内存预留参与节点选择，资源不足时服务任务可保持 pending。该调度机制与单容器运行时 memory reservation 的语义不同。[Swarm 文档][D6]

### 4.2 资源隔离：cgroup、systemd 与 Docker

**cgroup 把一组进程作为资源管理对象；systemd 和 Docker 提供管理入口。** Linux cgroup v2 可对 CPU、内存、块设备 I/O、任务数等设置控制。[内核文档][A9]

| 控制项 | 主要含义 |
| --- | --- |
| `cpu.max` / CPU 配额 | 限制一段时间内可使用的 CPU 时间 |
| `memory.low` | 在规定范围内提供尽力而为的内存回收保护 |
| `memory.high` | 超过边界后施加回收压力与节流，本身不触发 OOM kill |
| `memory.max` | 内存硬上限，无法回收到限额内时可能触发组内 OOM |
| `io.max` | 按设备限制块 I/O 的吞吐或操作次数 |
| `pids.max` | 限制组内任务数量 |

systemd 249 已有相应资源控制入口；例如 `CPUQuota=100%` 是一个 CPU 核的时间配额。实际能力还需核对内核、控制器和层级。[systemd v249 文档](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.resource-control.xml)

实施建议：容器限额由 Docker/正式部署配置管理，宿主机服务由 systemd 管理，避免多个程序覆盖同一控制值。不能认为限制了 `docker.service` 就限制了全部容器，必须检查实际 cgroup 层级。每个容器有限额，也仍需核算并发总量和主机基础服务的余量。[Docker 资源约束][A2]

### 4.3 监控：主机、容器与业务联合观测

| 组件 | 职责与位置 |
| --- | --- |
| node_exporter | 暴露主机资源指标，支持环境中可采集 PSI |
| cAdvisor / Docker stats API | 提供容器用量与性能线索；需验证容器发现和指标完整性 |
| process-exporter | 对选定进程分组采集，适合补非容器业务线索 |
| Prometheus | 采集时序数据、查询与计算告警规则 |
| Alertmanager | 告警聚合、路由、静默和通知；实际处置需要执行端 |
| Grafana | 作为指标展示层候选，与处置逻辑分开选择 |
| Zabbix Agent 2 | 官方 Docker 模板提供容器发现、指标及状态触发器 |
| Netdata / Telegraf | 可作为节点观测或采集替代，优先考虑团队已有体系 |

上述能力依据见 [node_exporter][S1]、[process-exporter][S4]、[Prometheus 告警架构][A3]、[Zabbix Docker 模板][D1]、[Netdata 告警扩展][S12]、[Telegraf Docker input][D7]。这些组件不是同一层面的互斥产品，应按职责组合。

**PSI（Pressure Stall Information）表示任务因 CPU、内存或 I/O 争用而停顿的时间比例。** 可从主机与 cgroup 读取，并支持阈值事件；它能提供比占用率更直接的压力线索，但不能单独确定应当终止哪个业务。系统级 CPU `full` 也不能按内存 `full` 的方式解读。[PSI 文档][S16]

### 4.4 自动处置：成熟规则工具与定制执行器

Monit 可按规则检查资源、执行外部程序及停止/重启服务。对 Docker 应按需要脚本/API 适配估算成本，包括容器发现、资源汇总、身份核验、冷却和恢复；不能描述成开箱即用的多容器保护器。[Jammy Monit 手册][A4]

Zabbix 支持远程命令；StackStorm、Event-Driven Ansible 等可把事件映射到动作或工作流。若团队已有这些平台，值得复用。但中心触发、网络传输、远程执行都可能延迟或失败，应单独保留本地紧急保护。[Zabbix 动作][D2]、[StackStorm][D3]、[Ansible Rulebook][D4]

若成熟工具的适配脚本逐渐承载复杂状态管理，才考虑轻量自研执行器。定制价值主要在公司的优先级规则、对象识别、执行协调与恢复验证，无须重新实现指标数据库或内核资源限制。

### 4.5 内存紧急保护：三个专项候选

| 候选 | 能力 | 主要边界 |
| --- | --- | --- |
| systemd-oomd | 利用 cgroup v2、PSI 等提前处置内存危机 | 需要正确配置候选层级；动作影响选中组内进程；不负责 CPU/磁盘保护 |
| earlyoom | 根据可用内存与 swap 阈值选择进程并发送信号 | 简单，但进程选择规则不能替代业务价值判断 |
| Meta oomd | 插件式检测器与动作，可定制内存策略 | 与 systemd-oomd 是不同项目，复杂策略再深入评估 |

来源：[systemd-oomd][A1]、[earlyoom][S9]、[Meta oomd][S10]。项目建议优先确定一个内存紧急处置主责，明确其与内核 OOM、Docker 恢复策略之间的关系，避免多个工具同时选择对象。

### 4.6 磁盘治理、取证与恢复

磁盘应分开治理：Docker 日志用驱动轮转，应用自管日志可用 logrotate；构建缓存可使用 BuildKit GC；持续增长的业务目录可评估文件系统配额及独立容量边界。配额可能把整机风险转化为某业务写入失败，应用仍需处理错误。[日志配置][A7]、[BuildKit GC][A14]、[XFS 配额][D8]

Below 支持历史 cgroup、进程和 PSI 的记录与回放，可作为缺少事故现场时的取证候选。resctl-demo/resctl-bench 可参考其资源竞争实验设计，但不是直接部署到五台机器的保护服务。[Below][A15]、[resctl 项目][A16]

硬件 watchdog、应用副本及故障转移属于故障后恢复分支。watchdog 需要设备支持且可能导致整机重启；五台机器也不必然具有互为备份的容量和数据条件。[Jammy watchdog 配置][D9] 内核 overcommit、swap 等调优需按业务评估，不应作为统一“防宕机参数包”。[内核 vm 参数][D10]

## 5. 面向组长的主要方案对比

选型分为三个层次：**比较主体实现、复用已有平台、按需补充业务治理。** 主体实现回答“监控、判断和处置由谁承担”；平台复用回答“现有工具能省掉哪些建设工作”；业务治理回答“怎样减少过载发生”。三者可以组合，无须六选一或同时建设六套系统。

所有组合都需要共同基础：工作负载资源限额、日志与容量治理、逐机业务优先级，以及动作审计和恢复验证。下面的成本是从零引入时的相对工程判断，没有实测人日或报价；已有平台会改变比较结果。

### 5.1 主体实现：重点比较 A、B、C

A、B、C 是三种不同的职责分配方式，适合作为主要选型对象。它们也并非绝对互斥，例如 Zabbix 可以配合本地规则工具；实际选择应明确哪部分负责采集、判断和执行，避免重复建设。

| 主体方案 | 组合与职责分配 | 定制量与运维负担 | 适用条件 | 主要缺口/代价 |
| --- | --- | --- | --- | --- |
| A 本地工具组合 | Monit 承载规则，Docker 适配脚本完成检查与处置，按需接集中监控 | 定制低至中；运维较低至中 | 对象相对固定、规则简单 | 容器发现、资源汇总、身份核验和状态管理会增加脚本复杂度 |
| B Zabbix 平台 | Agent 2 模板采集主机/容器数据，平台触发器与动作处理事件，补本地紧急保护 | 定制中；新建运维中 | 已有 Zabbix 或希望统一主机运维 | 模板减少采集工作，业务动作与断网时的紧急保护仍需补充 |
| C 指标平台与执行器 | Prometheus 等承担指标采集和告警，轻量本地执行器实现业务判断与处置 | 定制中至高；运维中 | 已有指标平台、策略较复杂 | 执行器需长期维护，采集器兼容性需测 |

**选择依据**：先确认公司已有平台，再比较规则复杂度、需要补充的代码以及维护责任。规则简单可先验证 A；已有 Zabbix 优先评估 B；已有 Prometheus 或需要复杂本地策略时比较 C。当前尚无实测数据支持无条件选定其中一种。

### 5.2 平台复用：用已有能力替代部分组件

这里保留 D、E 标识，方便对应前期材料。它们是平台复用路径，可以补充或替代主体方案中的监控、工作流和动作执行部分。

| 复用路径 | 能复用什么 | 与主体方案怎样配合 | 需要评估的代价 |
| --- | --- | --- | --- |
| D 自动化工作流 | StackStorm、Ansible 等已有 Runbook/Playbook 和多步骤恢复流程 | 例如 B/C 产生事件后调用既有流程；本地仍保留紧急保护 | 工作流适配、中心与网络依赖；从零建平台的运维负担可能较高 |
| E 商业/托管平台 | 已采购的监控、告警、工作流及执行连接 | 替代主体方案中已有产品能够承担的部分，再补业务规则和本地保护 | 订阅、接入权限、集成能力和维护成本；本次没有完成商业横评 |

E 仅核验了 Datadog 等代表性产品的工作流触发能力，不构成采购推荐。[代表性官方文档][D5] 若公司已有成熟平台，应先确认其可用能力，再确定 A/B/C 中还需建设哪些部分；没有既有平台时，不必为五台机器默认新建 D 或采购 E。

### 5.3 业务治理：F 可叠加在任何主体方案上

F 包括任务准入、队列、并发限制、请求限流，以及确有需要时的跨机调度。它作用于工作进入系统的过程，需要业务入口或调度器配合，可与 A、B、C 中任何一种组合使用。

例如，同一台机器同时启动十个大任务导致内存耗尽：主体方案负责发现危险、限制或停止任务；业务治理可以限制同时运行数量，让其余任务排队，减少危机发生。并发上限应根据任务用量和本机预算确定，不能照搬这个示例的数量。

已有 Kubernetes 时，应优先核查资源声明、节点预留与压力驱逐；节点压力驱逐不能简单依赖 PodDisruptionBudget 保证不中断。[Kubernetes 驱逐][S14]、[节点资源预留][S15] 新引入 Swarm/Kubernetes 则涉及业务改造、迁移及运维成本，需额外收益支撑。F 不能代替主机资源兜底，有状态业务迁移也需单独设计。

### 5.4 建议的决策顺序

1. **确认共同基础与现有资产**：资源预算、日志治理、业务优先级，以及已经部署的平台。
2. **选择主体实现**：从 A/B/C 中确定一到两个适合团队的候选进行验证。
3. **落实平台复用**：通过 D/E 替代可复用的部分，明确采集、判断、执行和恢复的责任归属。
4. **按原因补充业务治理**：任务集中进入或跨机分配导致过载时，加入 F。

汇报时可概括为：**主要比较三种主体实现，同时评估现有平台复用和业务侧预防措施。**

## 6. 参考环境的关键兼容性与实现边界

这些发现来自前期官方资料和 Anysearch 复核，尚不是本机故障诊断结果。

### 6.1 systemd 249 能力存在，但不能照抄新版命令

Jammy 手册确认已有 systemd-oomd，仍需检查 PSI、内存记账、swap 和实际启用范围。上游 249 没有新版 `--dry-run` 接口，发行版补丁及本机帮助需核实。无 swap 时仍可用压力动作，但反应窗口可能更短。[Jammy 手册][A1]

### 6.2 Docker 29.1 与采集器需要配套

官方 API 矩阵列出 Docker 29.1 最低 API 1.44、最高 1.52；上游已有 cAdvisor v0.49.1 在 Docker 29.0 使用 API 1.41 而采集失败的报告。这不能证明新版不兼容，但要求锁定版本并验证。[API 矩阵][A5]、[cAdvisor Issue][A6]

验收应确认预期容器全部可见、指标有效、容器重建后能重新发现，不能只看 HTTP 200 或采集目标 UP。Docker API 查询、动作执行端同样需要验证版本协商。

### 6.3 Monit 的安装版本决定可用规则和指标口径

前期核验时 Jammy 软件源列出 Monit `1:5.31.0-1`；6.0.0 的发布记录包含新增 swap 活动检查及 Linux 进程内存优先采用 PSS 的变化。不能拿最新手册和旧阈值直接配置软件源版本。外部程序检查还需显式规划超时和采样周期。[软件包][A10]、[发布记录][A11]

### 6.4 内存指标和参数需要读有效值

OpenContainers cgroup v2 实现把 `MemoryReservation` 写入 `memory.low`，不能当成 `memory.high`。Docker 的 `--memory-swap` 是内存与 swap 的总预算；与 `--memory` 相等意味着不给该容器 swap，具体运行时要核对。[实现源码][A12]、[Docker 限额][A2]

Linux 上 Docker CLI 内存显示扣除了部分缓存，而 API 提供原始值及缓存数据，二者不能不经处理直接比较。[Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/) PoC 应同时检查实际 `memory.low/high/max/swap.max` 与压力表现，避免仅凭配置文件宣称生效。

### 6.5 磁盘范围必须按实际存储布局确定

新安装 Docker 29 可能默认使用 containerd image store，升级安装可能保留经典驱动。采用前者时，镜像/快照可能位于 `/var/lib/containerd`，其他数据仍位于 `/var/lib/docker`；Docker `data-root` 不会同时迁移 containerd 数据。[存储说明][A13]

需要确认实际路径、数据卷、绑定挂载及其底层挂载点，分别监控字节和 inode。I/O 控制还受文件系统 writeback 等能力影响，应按真实存储测试。[cgroup 文档][A9]

### 6.6 日志和重启本身也可能放大故障

Docker 默认 json-file 若未配置轮转，日志可能持续增长；local 驱动自带轮转，是否切换需考虑现有日志采集。非阻塞日志缓冲可减轻背压，但满时会丢消息；修改默认日志设置也不自动改变已有容器配置。[日志文档][A7] 不直接用外部工具修改 Docker 管理的 JSON 日志。[官方限制](https://docs.docker.com/engine/logging/drivers/json-file/)

容器被终止后，Docker 或外部管理器可能重新拉起；须约定恢复主责和重试预算。优先通过 Docker 管理接口按容器操作，不把直接杀宿主机 PID 等同于停止容器。[重启策略][A8]

## 7. 建议的五台服务器保护设计

以下是可供候选方案共同采用的设计原则，不是已经开发的系统。

```text
每台服务器
  工作负载资源预算 + 主机基础服务余量
                    ↓
  主机压力 / 容器用量 / 业务健康
                    ↓
  判断风险 → 核验业务身份与允许动作 → 执行
                    ↑                  ↓
                    └── 冷却与恢复检查 ─┘
                                       │
                                       └→ 集中监控、通知、历史与审计
```

### 7.1 配置分层

| 配置层 | 内容 |
| --- | --- |
| 公共规则 | 采集项目、事件字段、超时、冷却、重试和状态流转原则 |
| 机器覆盖 | 核数、内存、swap、各挂载点、系统预留、能力探测、阈值与基线 |
| 业务覆盖 | 稳定标签/服务身份、负责人、优先级、允许动作、停止宽限时间、恢复方式 |

内存和磁盘阈值可结合绝对余量与比例；CPU/I/O 要结合机器能力、正常峰值和业务延迟。不能把参考机的一组百分比复制给全部机器。优先级名单由业务方确定，未登记对象先观测告警。

### 7.2 自动处置必须形成闭环

1. **触发**：普通风险通过持续窗口过滤突发，严重风险使用单独的预定规则；不能所有事件都等待相同长窗口。
2. **定位**：按完整容器身份、cgroup 和业务信息核验目标；若使用 PID，还需防止复用导致误操作。
3. **决策**：结合优先级、允许动作与预期资源收益，不只按占用排名选对象。
4. **执行**：优先业务减载或限制，按规则升级到优雅停止、必要时强制终止；并非所有资源都适用同一顺序。
5. **验证**：重新检查压力与关键业务；未恢复时记录失败并升级处理，不能无限终止更多对象。
6. **恢复**：达到恢复条件后再启动或放开限制，设置冷却及次数上限，避免反复振荡。

动作记录至少包含时间、机器、规则版本、触发数据、目标身份、动作和前后结果。采集与高权限执行可分离；Docker socket 是高权限入口，执行器应只暴露已登记操作。守护程序自身需要资源余量和受控日志增长。

### 7.3 “提前发现”的现实边界

一期可采用阈值、趋势和压力组合。容量风险可以辅助估算：

`预计触及安全余量的时间 ≈（当前可用容量 − 安全余量）/ 近期正增长速率`

这是工程上的局部线性近似，不适合直接触发终止；突发分配、缓存回收和周期波动都会使它失真。无需先引入机器学习才能实现有价值的保护。

用户态服务并不能保证在所有极端情况下及时运行。Docker daemon 失效时，本地采集可能仍工作，但 API 动作未必可用，因此需要事前资源限制及明确的失败升级路径。

## 8. 下一步验证计划与验收

### 8.1 推进顺序

| 阶段 | 工作与交付 |
| --- | --- |
| 环境盘点 | 五台规格、版本、存储、限额、监控与业务清单；尽量取得一次事故时间线 |
| 候选 PoC | 组长选择一到两个组合，在隔离环境完成指标和动作验证 |
| 只读观察 | 记录候选动作但不执行，覆盖业务峰值和批任务周期 |
| 有限试点 | 对一个明确可中断、可恢复的工作负载开启自动处置 |
| 评估推广 | 根据误判、开销、业务影响和维护成本，决定扩展或补充定制开发 |

无需等事故材料齐全才开始只读盘点。资源耗尽实验必须使用隔离测试环境与有界负载，磁盘实验使用独立测试卷。

### 8.2 候选使用同一套验证标准

| 类别 | 关键场景 | 需要的证据 |
| --- | --- | --- |
| 采集正确性 | 新建/重建容器、不同指标口径、客户端不兼容 | 容器清单与指标完整一致，缺失可识别 |
| 正常负载 | 高峰、缓存增长、短时 CPU 满载 | 没有未授权或不必要动作；业务在约定范围 |
| 内存 | 缓慢泄漏、快速增长、多容器同时增长 | 单组与全局边界有效，关键服务影响受控 |
| CPU/I/O | 后台任务持续竞争 | 处置改善关键业务，同时记录积压变化 |
| 磁盘 | 测试卷满、inode 耗尽、日志阻塞、缓存增长 | 仅操作允许范围，实际空间及业务恢复可确认 |
| 执行失败 | 权限不足、超时、目标退出、daemon 无响应 | 无误操作或无限重试，有明确升级记录 |
| 控制冲突 | 自动拉起、守护程序重启、中心断联 | 没有重复危险动作和重启风暴 |
| 停用恢复 | 关闭自动化、撤销限额、恢复服务 | 配置可回退，不可逆动作有业务恢复流程 |

验收指标包括发现时延、动作时延、缓解时间、业务恢复时间、误处置/漏检、组件 CPU/RSS/I/O 和日志开销。**目标数值待基线和业务要求确认，本报告不预设性能承诺。**

## 9. 希望组长明确的事项

明天讨论优先聚焦以下四项，不必一次补齐所有参数：

1. **可复用资产**：现在是否已有监控、告警、自动化平台和相关维护人员？
2. **一期目标**：优先保住哪些基础能力与业务？最希望复现或解决哪类事故？
3. **验证对象**：选择哪台测试机、哪一个可中断任务，以及哪一到两个候选组合？
4. **责任与边界**：谁确定逐机优先级、动作范围和恢复流程，后续由谁维护？

候选收敛后再补：精确版本与安装方式、软件许可和更新来源、离线部署要求、采购报价、人力估算、告警渠道和时延目标。

## 10. 汇报提纲与常见追问

### 10.1 约三分钟的口述主线

> 这次任务的目标，是在服务器资源过载时尽量保住整机和关键业务。目前已知有五台性能不同的服务器，大量运行 Docker；参考机是 Ubuntu 22.04.5、systemd 249、cgroup v2 和 Docker 29.1.3。具体历史宕机原因和业务优先级还需要现场确认。
>
> 调研下来，资源限制、监控和基础自动处置都有成熟实现，可以先组合验证。CPU 高占用适合结合压力和业务延迟做限流；内存临近耗尽可能需要停止低优先级容器；磁盘满还要靠日志、缓存和配额治理，杀进程不一定释放空间。因此方案需要同时具备预防、监控、定位、处置和恢复检查。
>
> 主体实现主要比较三种：Monit 加 Docker 适配脚本；Zabbix 官方 Docker 模板加动作与本地保护；Prometheus 体系加轻量本地执行器。三种都需要资源限额和日志治理作为基础。另有两个可叠加的层次：复用公司已有自动化或商业平台，减少重复建设；针对任务同时进入过多的问题，补充队列和准入控制。这些按层组合，不需要六选一。
>
> 我倾向于每台保留本地保护能力，中心统一看状态和历史，五台分别配置预算和优先级。当前需要注意 Docker 29 API 与采集器兼容、Monit 版本差异、内存 reservation 的真实语义，以及 Docker/containerd 的存储路径。这些边界已整理到报告，但还没有服务器实测结论。
>
> 希望这次先确认现有平台、关键业务和测试对象，选一到两个方案做相同条件下的验证，再决定是否需要自研以及最终采用哪种组合。

### 10.2 可能被问到的问题

**是否有现成软件，直接装上就能解决？**  
有成熟基础组件，但哪个业务能停、停止后怎样恢复、五台怎样分预算仍需业务规则。目前没有验证过一个产品能直接覆盖全部需求。

**为什么不直接写脚本，资源超过 90% 就杀最大的进程？**  
单一使用率不能区分正常负载与风险，最大的进程也可能最重要。还需要身份核验、持续判断、恢复检查和防止反复拉起；复杂度集中在这些环节。

**为什么这些方案可以组合？**  
A/B/C 是主体实现的选择，D/E 用已有平台替代其中部分组件，F 在业务入口减少过载。先明确主体职责，再考虑复用和补充，不是同时部署六套系统。

**到底推荐哪个？**  
优先复用现有平台。规则简单可先验证 A，已有 Zabbix 优先验证 B，已有 Prometheus 或需要复杂策略则比较 C；当前缺少平台现状和实测数据，不宜给无条件的唯一选择。

**能否保证不宕机？**  
不能。目标是减少资源故障概率和影响范围。突发耗尽、硬件故障、运行时失效或总容量长期不足，都存在单个守护服务无法解决的边界。

**五台机器要开发五套吗？**  
建议统一程序和配置结构，按机器覆盖资源预算，按业务覆盖优先级与动作。具体规则需用各机基线校准。

**是否需要 AI 预测？**  
当前无需作为前提。先建立可信指标、明确规则与执行闭环；有足够历史数据且证明规则不足时，再单独评估预测方法。

**接下来还要查多久？**  
可以暂停广泛检索，先汇报已有路线并确认环境。下一轮只针对入选候选的兼容性、成本或实验发现补查。
