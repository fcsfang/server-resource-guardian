# 五台服务器的方案收敛

第二轮 Anysearch 复核见[复核与新增发现](Anysearch复核与新增发现.md)；本文已同步主要修订。

## 1. 已确认范围

- 共 5 台服务器，性能存在差异，大量使用 Docker。
- 目前仅一台参考机版本已知：Ubuntu 22.04.5、systemd 249、cgroup v2、Docker 29.1.3。
- 需要覆盖 CPU、内存、磁盘等资源占用风险；具体历史事故表现尚不明确。
- 允许重启与终止进程，以避免整机不可用；业务优先级需要在真实环境中逐机确定。

这些是用户提供的信息，未连接服务器核验。不能推定其余四台使用相同版本，也不能把多资源预防范围当成已经证实的多种事故根因。这里讨论资源耗尽、争用与过载；硬盘损坏、CPU 硬件故障等需要独立的硬件告警和运维措施。

## 2. 参考环境意味着什么

参考环境具备评估 Linux 原生资源隔离的基础。systemd 249 上游已有 MemoryHigh、MemoryMax、CPUQuota、TasksMax 和 I/O 控制配置，实际效果仍取决于内核控制器、设备及层级配置。[v249 资源控制文档](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd.resource-control.xml)

systemd 249 已有 systemd-oomd，但还要核实 PSI、内存记账、服务安装/运行情况、swap 和实际监控范围。它只解决内存压力，不承担 CPU 或磁盘保护。上游 v249 没有新版的 `--dry-run` 接口，不能照抄最新版本的演练命令；应核对发行版补丁与本机帮助，用独立只读观测或隔离环境测试。[v249 oomd 文档](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemd-oomd.service.xml)、[新版接口及版本标注](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd-oomd.service.xml)

Docker 原生提供 CPU、内存等资源约束，是容器预算的首选入口。[Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)

不要将限制 `docker.service` 等同于限制全部容器：需要查看实际 cgroup 层级、driver 和父组。容器限额优先由 Docker/正式部署配置管理，宿主机服务由 systemd 管理，避免两个管理者反复覆盖同一控制值。

Docker 29.1 官方 API 矩阵的最低版本为 1.44，旧 cAdvisor 在 Docker 29 上已有 API 不兼容报告；这并非新版不可用的结论。Docker 29.1.3 与候选 cAdvisor、Docker SDK/API 客户端的组合尚未验证，详见[复核报告及官方来源](Anysearch复核与新增发现.md)。PoC 必须锁定组件版本，测试 API 协商、容器发现、指标采集、停止与重建；“能安装”不等于兼容性通过。

## 3. 建议架构：统一实现，逐机配置

**五台机器各有本地保护能力，监控视图可以集中。** 这是当前规模下的候选设计，不要求新建复杂调度平台。

| 层次 | 职责 | 复用方向 |
| --- | --- | --- |
| 资源预算 | 将单个任务的影响控制在边界内 | Docker 限额、systemd/cgroup、日志保留与容量治理 |
| 观测 | 同时看到主机风险和容器贡献 | node_exporter + cAdvisor，或 Docker API；已有平台优先 |
| 本地判断与处置 | 根据本机规则选择动作并验证结果 | 简单规则评估 Monit + Docker 检查/动作脚本；复杂规则再补轻量执行器 |
| 集中展示与告警 | 查看五台状态、历史趋势、处置记录 | 复用已有 Prometheus/Grafana、Zabbix 等 |

中心断网时，本地保护仍应工作。中心若部署在这五台之一，需要评估该节点不可用时的监控盲区和数据损失；当前不为五台机器预设复杂高可用系统。

## 4. 各资源使用不同的判据和动作

下表是建议验证的策略，不是可直接上线的阈值配置。

| 风险 | 判断依据 | 优先动作 | 关键边界 |
| --- | --- | --- | --- |
| CPU 竞争 | 持续占用、CPU PSI、运行队列、业务响应 | 限制后台配额或并发、降低争用 | CPU 满载可能是正常计算；重启未必减轻总负载 |
| 内存耗尽 | MemAvailable、内存 PSI、swap 活动、容器增长 | 停止接单/减并发，必要时停止可牺牲容器 | 暂停不释放内存；强压低限额可能触发 OOM |
| 磁盘空间/inode | 按挂载点的剩余量和增长速度 | 日志轮转、已授权临时文件清理、停止异常写入 | 杀容器通常不会清掉已有文件；卷和数据库数据不能随意删除 |
| 磁盘 I/O 竞争 | I/O PSI、设备延迟和工作负载读写 | 限流后台 I/O 或降低并发 | 限速不解决容量已满；设备/存储驱动组合需实测 |
| 任务数/FD 耗尽 | 线程和进程数、打开文件数、失败日志 | 限制增长、定位并停止失控任务 | 大量调用外部命令可能进一步消耗资源 |

网络带宽、连接数和 GPU 显存作为扩展项，先确认是否存在对应设备或业务风险，再确定采集与动作。无需等事故报告才能搭建上述观测，但自动处置效果最终要靠测试证明。

## 5. 不同机器怎样配置

建议配置按“公共默认值 → 机器覆盖 → 业务覆盖”组织，程序相同，最终生效配置可查询、可审计。

- **公共默认值**：采集项目、记录格式、动作超时、冷却与重试机制。
- **机器覆盖**：CPU 核数、内存总量、各磁盘/挂载点容量、系统预留、压力阈值及能力探测结果。
- **业务覆盖**：稳定的容器标签或服务身份、负责人、优先级、允许动作、停止宽限时间、重启预算、健康检查。

阈值不应全部写成同一个百分比。内存与磁盘容量可以结合剩余比例和绝对安全余量；CPU 按核心数量及正常峰值解释；I/O 按设备能力与业务基线校准。五台的资源预算需分别计算，不能把参考机配置直接批量复制。

业务优先级可先约定三类语义，具体名单稍后填写：

| 类型 | 建议默认策略 |
| --- | --- |
| 主机基础能力与关键业务 | 优先保留资源；是否允许紧急终止需逐项决定 |
| 允许中断且可恢复的服务 | 可以按规则限流或重启，控制频率 |
| 可牺牲的后台任务 | 危机时优先停止，记录任务与恢复条件 |

未登记业务先观测和告警。业务优先级既用于事前预算，也用于紧急选对象，不能仅作为按用量排序后的附加字段。即使具有较高处置权限，执行顺序仍需要显式配置。

## 6. 当前可以推进的工作

先在参考机获取只读清单：内核与 PSI、CPU/内存/swap、挂载点、Docker driver 和资源限额、日志设置、重启策略、容器归属及现有监控。随后在隔离环境分别模拟内存增长、CPU 竞争、日志增长和 I/O 拥塞。

以下两个候选是早期本地实现方向，不能代表完整选型空间。经覆盖审查，Zabbix 平台及现有自动化/采购平台复用也应参与条件比较，完整路线见[组长决策摘要](组长决策摘要与覆盖范围.md)。

1. **配置与脚本组合方案**：原生资源预算 + 现有监控 + Monit + Docker 适配脚本，检查身份发现、资源口径和动作协调的额外成本。
2. **轻量定制方案**：保留上述基础设施，增加支持逐机/逐业务配置的本地策略执行器，解决多资源判断、对象选择、冷却与恢复验证。

systemd-oomd 只作为内存紧急保护的专项候选。暂不因为需求覆盖面广就直接建设完整自研平台，也不要求先确认每个业务优先级才开始只读采集和测试。

此阶段的决策输出应是：成熟配置方案能覆盖哪些规则、还缺哪些业务能力、是否值得编码，以及五台机器各自的配置差异。尚未进行部署或实测。
