# 组长决策摘要与覆盖范围

日期：2026-09-16。状态：方案级桌面调研，可用于确定 PoC 候选；尚不足以直接批准生产部署。

## 1. 对完整性和权威性的说明

此前报告没有覆盖所有值得比较的技术路线，尤其对平台复用、任务准入、磁盘配额和故障恢复展开不足；过早将候选收敛到 Monit 与轻量自研。本文补齐这些决策维度，并撤回“仅比较两条路线即可”的过早收敛。

不能承诺穷尽所有产品、插件和实现组合。本项目采用的完整性标准是：**覆盖会改变架构、采购、开发量或运维责任的主要路线；每条路线说明职责、限制、采用条件与不采用理由；尚未调查的分支明确标注。** 不使用无依据的覆盖率或产品排名。

权威性分为三层：

- **已确认事实**：用户提供 5 台性能有差异的服务器；参考机为 Ubuntu 22.04.5、systemd 249、cgroup v2、Docker 29.1.3。尚未远程核验。
- **已查证能力**：官方手册、版本文档、实现源码说明组件提供什么；项目 Issue 仅证明特定条件下有人报告过问题。
- **项目判断**：组合方案、相对成本、优先级和试点顺序是工程建议；不能把它们写成厂商保证或实测结果。

完整版本、安装来源、运行时和文件系统未确认前，不给“兼容全部五台”的承诺。尚无性能测试、恢复时间、误杀率、工作量人日和采购报价，相关值不作虚构。

## 2. 需要解决的是完整的资源故障过程

| 环节 | 应纳入的技术路线 | 现有覆盖及本轮补充 |
| --- | --- | --- |
| 事前避免过量工作进入 | 任务队列、并发上限、请求限流、资源预算检查；需要跨机时评估调度器 | 原报告仅提减载，本轮补为独立业务治理路线 |
| 隔离单个工作负载 | Docker/systemd/cgroup CPU、内存、I/O、任务数控制 | 已较充分覆盖；仍需逐机有效值验证 |
| 约束存储增长 | 日志轮转、BuildKit GC、文件系统配额、业务数据保留、独立容量边界 | 补充磁盘配额与存储布局，不把清理当作唯一手段 |
| 持续发现风险 | 主机+容器指标、PSI、应用健康、外部可达性 | 已有主线；补比较其他采集与平台路线 |
| 找到可处置对象 | 容器身份、cgroup、业务标签、负责人和优先级 | 必须由业务登记，工具不能替代 |
| 实施处置 | 本地规则工具、自研本地执行器、平台远程动作或自动化工作流 | 补平台路线，避免默认必须自研 |
| 紧急内存保护 | 内核限额/OOM、systemd-oomd、earlyoom 等 | 已覆盖，主责与范围需明确 |
| 故障后恢复 | 服务恢复、任务重试、应用副本/故障转移；主机 watchdog 作为条件性兜底 | 原报告不足，本轮补范围和限制 |
| 复盘及长期改善 | 历史监控、Below 等取证、应用性能分析、泄漏修复与容量扩展 | 不将自动重启当作根因修复 |

以上是覆盖地图，不要求把所有机制部署一遍。监控、资源隔离、执行器和编排平台处于不同层次，不能直接当作互斥产品排名。

## 3. 可交给组长比较的主要组合路线

**所有路线都需要业务优先级、合理资源预算、动作审计和试点验证。** 表中成本为相对判断，假设从零引入；已有平台会明显改变比较结果。“本地保护”指部署在每台主机、能够在中心不可达时执行明确规则的组件。

| 路线 | 组合及承担的职责 | 定制开发量 | 新增运维负担 | 适用条件与主要代价 |
| --- | --- | --- | --- | --- |
| A：本地成熟工具组合 | 原生限额 + Monit + Docker 适配脚本；监控按需接入 | 固定规则较少时低至中；复杂规则会增长 | 较低至中 | 适合对象相对固定；自动发现、身份核验及冷却恢复仍需实现 |
| B：Zabbix 平台路线 | Agent 2 官方 Docker 模板 + 主机监控 + 触发器/受控动作 + 本地保护 | 中，模板可减少采集工作，业务动作仍需配置或开发 | 从零部署中；已有时较低 | 适合统一主机运维；中心远程动作不能独自保证断网时的紧急保护 [D1–D2] |
| C：指标平台 + 本地执行器 | Prometheus/node_exporter/容器采集 + Alertmanager/Grafana + 轻量本地执行器 | 中至高，主要在策略、身份与状态管理 | 中 | 适合已有指标平台或复杂策略；需要长期维护执行器，采集兼容性先测 |
| D：现有可观测平台 + 工作流 | 现有监控接 StackStorm 或 Event-Driven Ansible 等，再调用受控动作；本地留紧急保护 | 工作流适配中；有现成流程时降低 | 从零引入中至高 | 适合跨系统多步骤流程、统一执行审计；五台机器若无现有基础，平台成本可能不合算 [D3–D4] |
| E：现有商业/托管平台扩展 | 评估现有采购平台的主机/容器监控、事件到工作流能力及执行连接；本地留保护 | 取决于现有集成 | 平台自运维减少，但有订阅和连接维护 | 公司允许采购及数据接入时保留；本轮只核实代表性工作流能力，未做完整采购评估 [D5] |
| F：调度及应用治理 | 准入、限流、任务排队；必要时结合 Swarm/Kubernetes 资源声明、调度与恢复 | 业务改造及迁移较高 | 取决于是否已有编排平台 | 当主要原因是同时启动过多任务或缺少跨机分配时有价值；不能替代主机资源兜底 [D6] |

这些路线可组合：例如 B 配 A 的本地规则，C 配业务准入，D 处理较慢的多步骤恢复。**当前可决定的是进入 PoC 的组合，不宜直接决定最终生产配置。**

### 采集器与展示层的替代，不必都升级为独立架构

- Zabbix Agent 2 的官方 Docker 模板已确认具备容器发现、指标采集和状态触发器，但 Docker 29.1.3 的具体插件版本兼容性仍待实测。[D1]
- Telegraf 的 Docker input 已确认通过 Engine API 采集，若团队已有该体系，可作为采集替代；这不等于它提供完整自动处置。[D7]
- Netdata 已在原报告列为观测与告警脚本候选；cAdvisor、Docker API 等仍需在同一指标与开销标准下比较。
- 其他同类监控产品不逐一深评。若公司已经部署某产品，优先调查其现有能力，避免仅因为报告未列其名称就替换平台。

## 4. 原报告缺少或需要加强的方案

### 4.1 业务准入与并发控制

工程建议：对批处理、编译、训练、数据任务，在接收新任务之前检查并发槽位和资源预算；对在线请求评估限流、背压与降级。这需要业务入口支持，目前尚不知道实际应用，不能声称某个通用 Agent 可无改造实现。

Swarm 的 CPU/内存 reservation 可参与节点选择，无节点满足时任务保持 pending。该机制与单机 Docker 的 memory reservation 不应混为一谈；调度预留也不是运行时用量的万能保证。[D6]

采取这条路线的触发条件：事故主要来自任务同时进入，而单任务本身资源可预测。若是内存泄漏或容器失控，仍需隔离和终止能力。

### 4.2 磁盘配额与独立容量边界

XFS project quota 可约束目录树的磁盘使用；该能力来自文件系统，不能假定 Docker 某个参数能覆盖容器卷、绑定挂载和所有存储后端。[D8]

工程建议：在文件系统支持且业务允许时，评估业务目录配额，以及系统盘与高增长数据的容量隔离。配额耗尽会把问题转成特定业务写入失败，应用须能处理；新建分区、迁移目录或文件系统是独立变更，不应混入守护程序的日常自动处置。

### 4.3 平台动作与远程自动化

StackStorm 官方提供事件、规则、动作及工作流；Event-Driven Ansible 提供基于事件与规则触发动作的路径。[D3–D4] 这可以复用团队已有 Playbook/Runbook，避免把所有恢复步骤都写进本地 Agent。

工程判断：需要网络、中心调度或远程执行的路径更适合编排恢复和管理，不应未经时延与断网测试就作为突发内存耗尽的唯一保护机制。

### 4.4 故障后的可用性恢复

Jammy systemd 支持通过 RuntimeWatchdogSec 配置硬件 watchdog；需要实际设备支持。其作用是在失去喂狗时触发恢复，可能涉及整机重启，不能表述为避免业务中断。[D9]

应用副本、备用节点和故障转移属于进一步的可用性设计。五台机器不一定运行可互替的业务，不能因为数量为五就认定有冗余容量。当前重启/终止进程的权限说明也不能自动扩大为已批准整机重启；此处仅列选项。

### 4.5 内核调优与扩容

swap、overcommit 等策略可以影响内存分配与回收行为，但并不增加真实处理能力。内核文档提供 overcommit 控制语义；设置严格策略可能让分配更早失败，需结合应用评估。[D10]

扩容、拆分业务、优化泄漏或不受控缓存，应作为长期治理分支。当实际需求持续超过总容量时，终止低优先级任务只能改变损失分配，不能保证所有业务都继续完成。当前没有证据支持统一修改五台机器的内核参数或采购某种硬件。

## 5. 如何使组长拿到的材料足够支撑决策

建议汇报时明确区分两个决策阶段：

**现在：选择验证路线。** 根据现有监控/自动化资产、是否允许采购、规则复杂度和维护责任，从上表选择一到两个组合进入 PoC。A/B/C 是当前本地服务器场景的主要比较项；已有自动化或采购平台时 D/E 应进入同等比较；任务准入或跨机调度问题明显时加入 F。该排序是项目建议。

**实测后：决定生产方案。** 候选需要提交同口径证据：正常峰值误处置、突发资源耗尽、中心断联、容器重建、Docker daemon 失效、动作超时与重启冲突，以及采集/存储开销和业务恢复情况。指标来自既有[验证计划](需求确认与验证计划.md)。

每个进入 PoC 的候选最后至少补齐：

| 决策信息 | 当前状态 |
| --- | --- |
| 能力与限制、官方依据 | 主要路线已列；采购和特殊设备分支仅初筛 |
| 与目标版本、内核和存储后端的兼容性 | 发现部分明确风险，尚未完成机器级验证 |
| 五台实际资源预算与业务优先级 | 待逐机登记 |
| 所需配置、定制代码及维护负责人 | 可列任务，具体工作量需候选收敛后估算 |
| 运行开销、发现/缓解时间、误处置与漏检 | 待实验，不填想象中的性能数字 |
| 软件许可、离线安装、更新来源及维护周期 | 对最终候选逐项核对，尚未形成许可/采购审查结论 |
| 采购/存储/运维成本 | 相对比较已有；实际报价与人力成本待确认 |
| 停用、配置回退、数据及服务恢复 | 原则已列；需具体操作流程和演练 |

尚未深入：Windows、GPU 专项、网络拥塞/连接表专项、商业产品完整横评、五台整机高可用、全部内核和存储后端组合。原因是当前没有相应环境信息或不是已确认的一期主线；若组长明确纳入，应单独补查，不能视为已完成。

可以向组长这样表述：

> 本轮调研已识别面向 Ubuntu/Docker 资源故障的主要技术路线，并核验核心组件能力和部分版本风险。建议复用系统与平台能力，先用代表性机器做组合验证，再确定是否需要定制执行器。当前材料支持候选选型，兼容性、处置效果、成本和业务优先级仍需补充实测与现场信息。
