# PoC 验证蓝图

## 1. PoC 要回答的问题

1. 现有监控平台能否在 SSH 明显变慢或不可用之前发现资源压力？
2. 能否在一分钟内定位到责任容器、cgroup 或已配置的进程组？
3. 哪些信号能区分“正常满载计算”和“影响业务的资源争抢”？
4. 只读快照服务在 CPU、内存和 I/O 压力下能否保持响应？
5. 公司现有工具是否已经满足人工处置、审批和审计，从而无需自研 Guardian？

## 2. 环境前提

- 一台与生产版本接近、允许故障注入的非生产 Linux 主机。
- 明确 OS、内核、systemd、cgroup v1/v2、Docker/containerd/Kubernetes 版本。
- 测试业务或可丢弃容器，不使用真实生产数据。
- 测试机外部至少有一台监控端，避免被测主机失效时同时丢失指标。
- 获得 CPU、内存、I/O 和网络中断演练授权。

## 3. 推荐 PoC 拓扑

```text
监控端
  Beszel Hub -> 现有通知渠道 / 资源与容器界面
          ^
          | 指标抓取或现有 agent 上报
          |
测试 Linux 主机
  Beszel Agent（主机、Docker、systemd 服务）
  PSI/进程组补充采集（确认 Beszel 缺口后才增加）
  有界现场快照服务（observe-only）
  测试业务 / 压测容器
```

WSL2 PoC 使用隔离的测试 Beszel Hub/Agent 或公司批准的测试系统，不把实验告警和测试主机直接混入生产系统。

## 4. 工作包

### WP-0：资产与故障样本

- 收集最近 3 至 5 次资源耗尽事件的指标、OOM、内核日志和重启时间。
- 确认主机角色、业务责任人、容器运行时和带外管理能力。
- 输出保护名单初稿和测试对象白名单。

### WP-1：只读观测

- 开启主机 CPU、load、MemAvailable、swap、磁盘、I/O、网络、文件描述符和进程数指标。
- 内核支持时采集 CPU、memory、I/O PSI。
- Docker 场景采集容器 CPU、内存、网络、块 I/O、限制值和重启次数。
- 对少量已知进程按业务名称分组；禁止 PID 作为常驻指标标签。
- 记录 exporter 的抓取耗时、样本量和被监控主机开销。

### WP-2：分级规则

规则以“强度 + 持续时间 + 压力 + 业务影响”组合判断：

- CPU 预警：持续高利用率，同时观察 load、运行队列和 CPU PSI。
- 内存严重：MemAvailable 持续降低，同时出现 memory PSI 或持续 swap 活动。
- 内存紧急：发生 OOM/OOM Kill，或业务健康与高 memory full pressure 同时恶化。
- I/O 严重：I/O PSI、设备延迟和业务延迟同时升高。
- 管理面异常：SSH 探测、指标抓取和快照心跳分别记录，避免把单点探测失败误判为主机宕机。

具体阈值用历史数据和压测校准，不把配置样例中的占位值直接用于生产。

### WP-3：有界现场快照

告警时收集以下摘要，并为每项设置超时、输出上限和总磁盘配额：

- 主机时间、启动时间、load、内存和 swap。
- `/proc/pressure/*` 与 OOM/cgroup memory events。
- Top CPU、内存、I/O 进程及进程树。
- systemd unit/cgroup 资源摘要。
- Docker 容器状态、限制和一次性资源快照。
- 最近的内核、OOM、Docker 和目标服务日志。

首版只采集，不终止、不暂停、不重启任何对象。

### WP-4：资源保护验证

- 给测试业务设置 CPU、内存和 I/O 边界，比较设置前后的故障影响范围。
- 将快照服务放入独立 systemd slice，验证 CPU/IO 权重、内存保护、自身上限和自动重启。
- 验证 `MemoryMin`/`MemoryLow` 的祖先 cgroup 配置确实生效，不能只检查 unit 文件文本。
- 有 swap 与无 swap 场景分别记录内存压力发展速度，但不得在生产主机直接试验。

### WP-5：人工 runbook

建立固定、可审计的人工流程：

1. 确认事件仍在发生并查看现场快照。
2. 识别对象的业务所有者、systemd unit、cgroup 或容器 ID。
3. 检查保护名单、集群副本数和维护窗口。
4. 优先限流或优雅停止，再考虑强制终止。
5. 验证资源与业务恢复；未恢复时停止重复动作并升级带外处理。

## 5. 故障演练矩阵

| 场景 | 方法原则 | 期望结果 |
| --- | --- | --- |
| CPU 饱和 | 在受限测试 cgroup/容器中逐步增加计算负载 | 能区分高利用率与高 PSI，定位测试对象，监控仍响应 |
| 内存压力 | 在设置内存上限的测试 cgroup/容器中逐步申请内存 | 提前告警、捕获 PSI/OOM 事件，不影响保护对象 |
| I/O 争抢 | 对测试文件系统和受限 cgroup 施加有界 I/O | 定位设备和对象，快照不因 I/O 阻塞无限挂起 |
| Docker 失控 | 测试容器消耗 CPU/内存并触碰限制 | 宿主与容器指标能关联，宿主关键服务仍可用 |
| 中心失联 | 临时隔离测试机到监控端的网络 | 中心识别失联，本机快照有界缓存，恢复后正常继续 |
| 保护对象操作 | 对保护名单对象提交模拟动作 | 在执行前被拒绝并记录审计 |
| 重复告警 | 连续制造相同压力 | 告警聚合、恢复迟滞和冷却符合预期 |

## 6. 建议验收指标

以下是 PoC 目标，最终值由导师和运维负责人确认：

- 受控故障开始后 60 秒内产生包含主机和原因的告警。
- 每个受控场景均正确定位到测试容器、cgroup 或进程组。
- 告警快照在约定超时内完成，任一子命令卡住不会阻塞整体服务。
- 压测期间监控和快照服务保持心跳，且自身不会无界增长。
- 自动变更动作数量为 0；所有处置通过人工 runbook。
- 额外采集开销、时序基数、网络流量和磁盘增长均被量化。
- 测试结束后业务健康与资源指标出现恢复事件。

## 7. PoC 输出物

- 环境与资产清单。
- 指标字典、仪表盘和告警规则。
- 每个故障场景的时间线、快照和结论。
- exporter/快照服务资源开销报告。
- 保护名单、人工 runbook 和带外兜底流程。
- “复用现有工具 / 引入 Monit 或 systemd-oomd / 开发 Guardian”的决策记录。

## 8. 停止条件

出现数据丢失风险、测试负载越出 cgroup、核心网络或管理服务异常、无法确认目标身份、监控服务自身失控时，立即停止故障注入，不继续验证自动处置。
