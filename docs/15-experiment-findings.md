# 实验关键结论汇总

更新时间：2026-09-18

> 用途：将 EXP-001 ~ EXP-006 的技术发现汇总为可执行的工程结论，供架构设计和汇报使用。每条结论标注来源实验和结论类型（观测/判断）。

## 1. 资源危机的失效机制

| 发现 | 结论类型 | 来源 | 工程意义 |
| --- | --- | --- | --- |
| 宿主机级内存耗尽导致系统崩溃（非 SSH 变慢） | 观测 | EXP-005 | 监控必须在内存到达临界前告警，而非等系统不响应 |
| sshd 被内核 OOM killer 保护（oom_score_adj=-1000） | 观测 | EXP-005 | OOM killer 不会杀 sshd；SSH 失效 = 整机崩溃 |
| Docker 容器内资源消耗被 cgroup 隔离 | 观测 | EXP-002/005 | 容器内的内存泄漏不会拖垮宿主机 |
| Docker 容器无限制时多容器竞争可达 94%+swap 85% | 观测 | EXP-005 | 多容器无限制竞争会逼近系统极限 |
| CPU 100% 时 SSH 仍可用（延迟 117-483ms） | 观测 | EXP-004 | CPU 竞争不是主要风险，**内存才是** |
| --pids-limit 有效防止容器内 fork bomb | 观测 | EXP-005 | PID 限制是有效的资源边界手段 |

## 2. 检测-定位-处置-恢复管道时效

| 阶段 | 耗时 | 来源 | 说明 |
| --- | --- | --- | --- |
| 泄漏开始 → 警告（70%） | 110s | EXP-006 | 可用预警窗口 |
| 警告 → 临界（85%） | 31s | EXP-006 | 危机升级窗口 |
| 定位肇事容器（docker stats） | **< 1s** | EXP-006 | 即时 |
| 处置：docker stop | **13s** | EXP-006 | 瓶颈（SIGTERM 等待） |
| 处置：docker kill（估算） | **~1s** | EXP-006 | 可优化 |
| 恢复确认 | 2s | EXP-006 | — |
| **总响应时间** | **15s（可优化至 ~3s）** | EXP-006 | 远快于崩溃时间（>60s） |

## 3. 架构决策

| 结论 | 对架构的影响 | 来源 |
| --- | --- | --- |
| Guardian 必须自己做实时检测（~1s），不能依赖 Beszel | Beszel 采样周期 60s，从 70% 到 85% 只需 31s，等 Beszel 发现时可能已崩溃 | EXP-006 |
| Beszel 保留为历史数据看板和告警通知 | Beszel 的长处是存储、可视化和历史告警，不适合实时检测 | EXP-006 |
| docker stats 是定位肇事容器的最快方式 | < 1s 返回，比查 Beszel API 或 cgroup 文件更快 | EXP-006 |
| docker kill 比 docker stop 更适合紧急止损 | 13s → ~1s，但需保护名单确认后才可使用 | EXP-006 |
| Docker 资源限制（--memory/--cpus/--pids-limit）是有效的预防手段 | 但属于运维配置，不是 Guardian 的职责 | EXP-002/005 |
| Guardian 的最小功能 = 实时检测 + 容器定位 + 保护名单校验 + 受控终止 + 恢复验证 | 不需要重写监控或 OOM kill 逻辑 | EXP-003/006 |

## 4. Guardian 最小功能清单

基于 EXP-003 缺口分析和 EXP-006 管道验证：

| 功能 | 优先级 | 说明 |
| --- | --- | --- |
| 实时内存监控（轮询 /proc/meminfo） | P0 | 1s 间隔，检测异常增长 |
| 容器定位（docker stats） | P0 | 确定哪个容器消耗最多 |
| 保护名单 | P0 | 配置文件列出不可终止的容器/服务 |
| 受控终止 | P0 | 先 docker kill，保护名单校验后才执行 |
| 恢复验证 | P1 | 确认内存回落后记录审计日志 |
| 动作前快照 | P1 | 保存目标容器的 docker inspect + 进程信息 |
| 通知 | P2 | 调用 webhook / 写日志 |
