# 任务背景与需求基线

文档状态：草案  
基线日期：2026-09-16  
需求来源：实习任务截图及任务背景补充

## 1. 背景

生产服务器会出现 CPU、内存或其他资源长期高占用，严重时整机失去响应、SSH 登录失败并导致业务中断。当前通常依赖人工发现和重启服务器，恢复时间长，也容易丢失故障现场。

原始任务要求可归纳为：在 CPU 或内存占满、SSH 失效的情况下，服务器上仍有可用的高优先级 agent；该 agent 能提供进入和诊断能力，对高占用进程或 Docker 工作负载执行受控处置，尽量避免整机重启。

## 2. 项目目标

1. 实时了解服务器、进程、容器和 cgroup 的资源状态。
2. 在资源耗尽之前，通过趋势和系统压力信号识别危机。
3. 危机发生时保存足够的现场证据，明确资源消耗来源。
4. 保留一个资源受保护的本机 Guardian 和独立控制通道。
5. 按策略执行通知、限流、优雅终止、强制终止或容器重启。
6. 验证资源恢复和业务健康，并完整记录操作审计。
7. 尽可能避免服务器重启，降低生产中断时间和人工处置成本。

## 3. 术语与边界

- **监控端**：采集、存储、展示指标并产生告警的成熟组件。
- **Guardian**：部署在被监控主机上的轻量守护服务，仅承担本机快照、策略判断和受控处置。
- **控制端**：在中心侧发出经过鉴权的人工或策略指令。
- **危机**：资源压力持续升高，已经或即将影响业务、SSH 或系统调度。
- **自动处置**：无需当次人工确认即可执行的动作，只允许作用于预先批准的对象和动作。

本项目不承诺仅靠一个高优先级进程解决所有宕机场景。内核死锁、宿主机掉电、磁盘或网络硬故障仍需云控制台、BMC/IPMI/iDRAC/iLO 等带外能力。

## 4. 功能需求

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-001 | 主机指标采集 | CPU、负载、内存、swap、磁盘容量与 I/O、网络、文件描述符、进程数可查询 |
| FR-002 | 压力与异常事件采集 | Linux PSI、OOM/OOM Kill、内核关键日志和服务存活状态可查询 |
| FR-003 | 责任对象定位 | 告警能关联到高占用进程、进程树、容器及 cgroup，而不是只有主机总量 |
| FR-004 | 危机判断 | 同时使用强度、持续时间、趋势和压力信号；具备恢复阈值与防抖机制 |
| FR-005 | 分级告警 | 至少支持预警、严重、紧急三级，并包含主机、时间、原因、Top 对象和处理入口 |
| FR-006 | 现场快照 | 处置前记录进程、容器、资源、连接、系统日志和最近动作，快照可追溯 |
| FR-007 | 人工处置 | 授权人员可对明确目标执行限流、SIGTERM、SIGKILL 或容器重启 |
| FR-008 | 自动处置 | 只对规则白名单内对象启用；默认关闭；具备次数上限、冷却和熔断 |
| FR-009 | 保护机制 | PID 1、Guardian、SSH、监控组件和公司指定核心服务不可被误杀 |
| FR-010 | 结果验证 | 动作后验证资源是否恢复、目标是否退出或重启、业务探针是否健康 |
| FR-011 | 审计 | 记录触发指标、规则版本、操作者、目标、动作、结果和时间 |
| FR-012 | 配置管理 | 阈值、保护名单、动作授权和通知渠道可配置、可校验、可版本管理 |
| FR-013 | 心跳与失联判断 | 中心端可区分 Guardian 失联、主机失联、采集异常和业务异常 |
| FR-014 | Docker 支持 | 能定位容器与宿主进程关系，优先使用容器级限制和编排器语义进行处置 |

## 5. 非功能需求

| 编号 | 需求 | 初始标准 |
| --- | --- | --- |
| NFR-001 | 低开销 | 空闲和正常负载下的 CPU、内存、磁盘开销需经 PoC 测量后确定上限 |
| NFR-002 | 抗压生存 | Guardian 使用独立 systemd/cgroup 资源保护、OOM 保护及自动重启 |
| NFR-003 | 安全 | 控制通信需双向鉴权和加密；执行权限最小化；拒绝任意 shell 命令 |
| NFR-004 | 可用性 | 中心端不可用时，本机仍能采集快照并执行预批准的本地策略 |
| NFR-005 | 可维护性 | 配置有 schema 校验，规则有版本，部署可回滚，升级不中断监控 |
| NFR-006 | 兼容性 | 首版以待确认的 Linux 发行版、systemd、cgroup 版本和 Docker 版本为准 |
| NFR-007 | 可观测性 | Guardian 自身暴露健康、延迟、队列、错误和动作计数指标 |
| NFR-008 | 数据治理 | 指标、日志、快照、审计的保留周期和敏感信息脱敏符合公司要求 |

## 6. 告警等级初稿

阈值必须通过公司服务器基线和压测校准，以下仅定义含义，不作为生产默认值。

- **预警**：资源使用持续偏高或增长异常，但业务和交互仍正常；通知并观察。
- **严重**：PSI、可用内存、I/O 等表明业务已受影响；自动取证并请求人工确认。
- **紧急**：系统接近不可操作或已触发 OOM；只执行预批准的保命策略并升级通知。

## 7. 首版验收场景

1. 在测试机上用受控压测逐步增加 CPU 压力，验证告警、Top 进程定位和恢复通知。
2. 逐步消耗可用内存并制造 PSI，验证 Guardian 未被 OOM Killer 选中且能保存快照。
3. 制造 Docker 容器资源失控，验证定位到具体容器并经人工批准完成处置。
4. 暂停中心监控或断开网络，验证本机缓存、心跳失联判断和恢复后补传。
5. 尝试对保护名单对象执行动作，系统必须拒绝并产生审计记录。
6. 连续触发相同规则，验证冷却、次数上限和熔断生效。
7. 动作后资源仍未恢复时，系统升级告警而不是无限重复终止对象。

## 8. 明确不在首版范围

- 自动分析所有业务根因或替代应用性能监控。
- 在没有白名单和演练的情况下自动杀掉任意高占用进程。
- 替代高可用、容量规划、备份恢复或带外管理体系。
- 直接在所有生产主机全量发布未经灰度验证的 agent。
