# 01_cover

本次汇报先回答现成资源保护策略能否满足我们的需求。我们按内存、CPU、磁盘和跨资源管理来比较，优先通过配置和试点解决问题。只有出现明确的业务缺口，才展开后面的观测、定位与处置设计。因此，后半部分是备选补充方案，不表示已经决定开发。当前是技术调研，没有部署或故障实测结论。

# 02_context

任务来自服务器资源占用过高、影响生产的风险，希望自动发现并处理危机，尽量避免宕机。必要时可能需要重启服务或终止进程，但是否允许以及具体对象必须由公司提供。我们目前不能假定每次高占用都是同一种故障，也不能根据参考机器推断所有服务器配置一致。要先核对事件记录、业务优先级和允许动作，再判断现成策略能否达到保护目标。

# 03_landscape

现成方案不仅有接口，还包含配置后自动运行的策略。内存应急工具能够自行检测压力、选择对象和终止；CPU、IO和任务数量限制由内核持续执行；日志治理根据大小和保留条件轮转清理；Monit对已知服务执行配置的恢复；Kubernetes和Slurm在统一管理的工作负载范围内提供驱逐或调度。这些工具可以组合，不是只能选一种。

比较时统一回答管理什么对象、何时触发、如何选择、采取什么动作，以及需要配置什么和覆盖不到什么。“完整方案”只针对它声明的保护范围，不能等同于所有故障都能自动处理并保证关键业务恢复。详细官方来源随下列各资源页面列出。

# 04_oomd

systemd-oomd是一套本机内存应急处置机制，能够自己采集压力、选择符合条件的对象并终止，不需要先接入Prometheus，也不需要我们重写相同循环。这里按Ubuntu Jammy的systemd二百四十九系列手册核验。

它有内存压力和swap相关触发路径。压力超过阈值并持续配置时长后进入处置。PSI表示任务因资源不足而等待的时间比例，并非内存已用百分比，不能把两种阈值混用。

候选位于被监控单元的后代cgroup中，需符合叶节点或组级OOM等条件。压力路径参考回收活动量，swap路径参考满足条件对象的swap用量，不是简单选择内存占用最大的容器。avoid和omit可以降低选择优先级或排除对象，但有属主、扩展属性和非递归作用等限制，必须按层级核验。

动作是向选中组的进程发送SIGKILL，以缓解内存危机，不是Docker stop式优雅退出，也不会等待保存任务进度。它持续观察资源条件，但不替我们验证公司业务恢复。适用前提是业务允许牺牲一部分负载。还需验证Docker的cgroup驱动与层级、关键业务保护、swap、自动重启以及和其他执行器的协调。

# 05_memory_choices

三种方案都面向内存危机，但管理粒度和策略表达不同。systemd-oomd使用PSI或swap条件，在cgroup层级选择并强制终止，当前参考环境已有systemd和cgroup第二版，因此值得先评估适配性，但不等于已启用或适合生产。

earlyoom检查可用内存和swap，默认参考oom_score选择进程，还可设置偏好并发送终止信号。它管理进程，进程到容器和业务的映射需要另核；避免偏好不等于绝对保护。Meta oomd是另一个独立项目，使用PSI和cgroup第二版，通过规则和插件表达策略。可先评估已有插件，需要时再扩展，不能预先认定必须开发。

三者都需要确认终止范围与业务后果。如果systemd-oomd的组级策略足够，就优先配置试点；不够再比较其他策略。不要让多个独立终止策略无协调地同时作用于同一业务。本次没有比较性能、开销或运维成本的实测结果。

# 06_limits

CPU争抢通常先通过资源份额治理。Docker的CPU限额和权重，或systemd的CPUQuota与CPUWeight，会由底层内核控制器持续执行。管理员声明资源预算后，不需要自己写一个程序不断检测并重复设置同一限额。限额约束CPU时间，权重影响竞争时的相对分配；CPU利用率高可能只是正常计算工作，不能直接视为故障。

磁盘IO限制控制指定组在指定设备上的带宽或IOPS。它解决读写竞争，不清理文件，也不增加磁盘可用容量，设备与文件系统上是否生效需实测。Docker的pids-limit和systemd的TasksMax限制任务数量，达到上限时阻止继续创建，线程也影响计数，不能理解为会自动杀掉已有任务。

这些方案需要配置对象、预算和优先级，并验证业务性能、控制器支持和作用范围。Docker管理的容器优先走Docker的配置，systemd或上级分组的限制需要尊重cgroup管理归属，避免多个管理者无协调修改。

# 07_disk

磁盘空间要按数据归属治理。Docker local日志驱动可以按大小轮转并按数量保留，修改daemon默认日志配置不会自动改变现有容器，要评估应用到已有任务的步骤。容器写入卷里的文件也不一定属于该日志驱动的管理范围。

journald管理自己的journal文件，按照空间和保留规则回收归档。它不清理其他应用数据，也不能保证其他业务填满磁盘后主动回收出任意目标空间。logrotate针对明确配置的日志路径，通过定时运行检查周期或大小条件后轮转，检查频率影响实际时效；应用如何重新打开文件也需要配置，copytruncate存在少量日志丢失窗口。

数据集、模型文件、数据库和持久化卷仍需公司明确保留和删除规则。停止容器并不一定释放这些空间。Docker私有日志应通过其日志机制管理，不建议让外部轮转工具直接接管。这里的自动治理已有成熟机制，但不能授权自动删除未知业务数据。

# 08_cross_resource

跨资源方案应按工作负载选择。Monit适合明确的固定服务，周期检查资源或健康状态，在满足配置条件后执行预先定义的停止和重启。已有规则执行机制，但动态Docker容器的发现、业务映射和操作仍需适配。

Kubernetes的kubelet有节点压力驱逐机制，会根据内存、磁盘、inode或PID等信号，先尝试适用的节点资源回收，再按策略驱逐Pod。由控制器管理的工作负载可按声明补建，不代表一定在原节点立即恢复。CPU高占用不是同类节点压力驱逐信号。采用它需要把工作负载纳入Kubernetes，不是安装后接管现有独立Docker。

Slurm面向作业资源申请、排队、分配和约束，可管理CPU、内存、GPU，并配置优先级和抢占。需要通过调度器提交任务、正确配置资源约束。暂停不会释放作业仍占用的内存和GPU分配，因此不能把暂停作为内存危机的通用解决办法。

当前先核验本机策略，有统一容器编排或多用户作业调度需求时再比较迁移和管理成本，不能仅为少量阈值检查直接推荐大平台。

# 10_contract

只有确认现成策略存在覆盖缺口，才需要展开这一部分。观测把来源数据整理成结构化指标，包含对象身份、用量、变化、压力、时间和有效性。定位结合这些字段及公司维护的业务权限与规则，生成候选、依据和建议动作，可以补查缺少的证据，也可以返回无候选。处置在执行前复核当前状态，调用获准的动作接口，再输出执行状态、资源结果和业务检查结果。

这三段不是三个必须独立部署的软件，也不是用自然语言互相聊天。B增长多是指标证据，B符合本次处理规则是候选决策。已有systemd-oomd等工具已覆盖的循环不需要重复实现。若现成执行器与补充程序同时存在，要明确对象范围、优先级与防重复控制，避免相互冲突。

# 11_observe_options

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

这一页让各工具回答同样四个问题：谁占得多，谁近期增长，资源是否真的紧张，以及业务有没有受到影响。当前用量帮助找对象，历史变化帮助缩小范围，等待和限流信息帮助判断压力，业务耗时和错误则帮助判断影响以及后续是否恢复。它们是四种需要的信息，不是工具从低到高的等级。

先增加一个基线：保护程序直接从本机Linux和Docker读取信息。这本身也是可行的选择。当前容器用量可通过Docker统计接口读取，程序要处理单位和内存口径，例如Docker命令行与API对缓存的处理不同。近期增长需要连续采样、保存一段历史并自己计算，单次读数不能回答。资源压力也不是平台独有的信息，Linux的主机和cgroup压力文件可以提供PSI，cgroup的CPU统计可提供限流信息；但程序要核对内核与控制器支持、权限、文件路径以及容器对应关系，并解析数据。内核自带的累计计数和短窗口统计不等于完整的容器用量历史库。业务影响仍需要自己检查接口或读取应用暴露的指标，操作系统不能凭空知道业务错误率。

因此，直接读取并不代表只能拿到粗略信息；平台主要帮助复用已有采集、历史保存和查询计算。只需要少量本机指标时，直接读取可能更合适；需要很多细项或已有历史时，再衡量采集器或平台能节省多少开发工作，以及引入的组件开销。紧急保护的取数位置和操作前复核仍应结合本机可靠性设计。

先看当前用量，这几种组合都能提供容器内存等信息，因此这一列本身分不出胜负。Beszel提供基础容器用量和已保存的历史，如果公司已有它，且这些信息足够，可以先复用。需要自动筛出近期增长的容器时，本方案要补上读取历史和增长判断；这不代表已证明Beszel不存在任何其他扩展。官方基础指标说明没有确认PSI和CPU限流字段齐全，需核对实际版本或另外采集。业务耗时和错误率也不能从资源用量推出来，需要另外接入。

Prometheus需要配套采集器。这里具体指node_exporter提供主机PSI，也就是资源等待统计，cAdvisor提供容器用量和CPU限流等指标。主机等待不能直接归因到某一个容器。程序可以提交查询表达式，计算内存变化并对候选排序，例如使用适合内存这类可升降数值的变化或斜率计算；不能把累计计数器的速率公式不加区分地套用。返回计算结果是它的一项明确能力，但表达式仍需编写，样本时间和容器标签仍要校验。业务信息需要应用暴露指标，再配置采集，并不会自动出现。

Zabbix的Agent二和Docker模板也能提供容器用量，模板列有CPU限流信息，但不能据此推定所有压力指标都有。PSI需要另行核对或补采。Zabbix不仅能存历史，还支持配置计算项，根据已有监控项计算变化，因此不能把能计算当成Prometheus独有的能力。区别是这里配置一个按更新周期运行的计算项，而Prometheus可以在查询时提交表达式。两者都需要明确窗口和计算口径。业务侧可以接入应用数据或配置接口检查；接口探测耗时与真实用户请求耗时仍是不同证据。

Netdata本机Agent提供容器用量、历史和聚合查询，官方容器指标列表还列出容器PSI和CPU限流。因此，如果我们缺的是本机资源等待等细项和近期历史，它值得试验。这里选择的实现路径是读取本机历史，再实现按增长筛选候选；不是宣称Netdata完全没有计算能力。业务信息同样需要对应应用集成，或应用自己提供指标。所有列出的字段是否在目标内核、权限和Docker版本下可用，仍需实测。

实际选择时，已有基础历史而且够用就先复用；需要本机压力细项时试验Netdata；需要灵活计算和筛选结果时评估Prometheus；已有Zabbix则先核查模板和计算项。若多个工具都满足所需信息，这一维度就不能硬分胜负，再比较取数位置和接入工作量。Monit主要面向固定服务检查和动作，放在第十六页比较，不强行放进这张动态容器信息表。

这些数据只帮助筛选候选。信息缺失不能当作零，业务是否允许停止仍由公司提供，执行前还要本机复核当前状态和目标身份。表格依据官方文档能力，并非Docker二十九与cgroup第二版组合的实测结论。

# 12_data_comparison

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

这一页比较的核心，是数据平台能替后面的判断完成多少计算。两者都能提供指标和历史，因此不能把Beszel概括成只有展示、没有计算。

Beszel配套Agent采集主机和容器指标，平台提供历史查看、既定统计和告警，也能通过REST API读取记录。它适合快速建立基础监控。需要更复杂的自定义历史计算时，本方案通常把计算放到自己的程序里，具体API字段、历史粒度和版本需要核对。

Prometheus通常从node_exporter、cAdvisor或应用暴露的指标接口拉取数据，保存时间序列。PromQL可进行筛选、聚合、变化计算和排序，记录规则可以定期计算并保存结果。采集器、标签、表达式和规则需要配置，它不会自动知道我们的判断标准。

以一个假设需求为例：筛选过去10分钟内存净增长、当前超过2 GB的容器，并按增长量排序。阈值只是示例，不是生产建议。Beszel路线获取可用历史记录，由程序算增长、筛选和排序；Prometheus路线可以用PromQL计算，程序读取结果。这里使用净增长而非严格近期增长，避免把首尾变化误当成每个采样点都在增长。

如果仅需基础指标和少量简单条件，可以先评估Beszel；如果经常需要自定义历史计算、多指标组合和复用计算结果，Prometheus更有优势。不能据此断言总开发量必然更少。无论哪种路线，排名都不是根因或执行授权，公司业务权限、执行前本机复核和恢复验证仍需实现。

# 13_locate

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

定位要交出的结果，是一个有依据而且允许处理的候选。观测告诉我们S1内存持续紧张，定位继续回答三个问题：对象是谁，处理它为什么可能有帮助，以及公司是否允许这样处理。

先确认B的完整容器身份、所属业务和当前状态。历史数据可能指向已经销毁的容器，同名容器重建后也不一定是原来的对象，因此不能只按名字执行。然后结合用量、近期增长和资源压力判断，停止B可能释放内存。这是筛选候选的依据，不是已经证明B就是事故根因，更不能精确保证能够释放多少。

最后核对业务配置。贯穿案例里，B是公司允许中断的离线任务，A是不能自动停止的数据库；这只是解释流程的假设，真实清单尚未提供。Docker标签可以承载业务身份等元数据，但标签本身不是可信授权的替代品，权限应来自公司认可并维护的配置。未知业务不进入自动处理名单。

定位交出的候选包括完整身份、资源证据、允许动作和先后顺序。多个候选之间按公司规定的优先级和预期缓解效果选择；如果没有安全候选，就告警转人工。定位不直接发出停止命令，处置环节仍要复核风险、身份和最新权限。下一页据此比较各组合能省下多少筛选工作。

页面输出使用示意字段，实际应传递完整对象ID、建议动作、指标和规则编号，不是自然语言。B、A与S1均是假设对象。

# 14_locate_tools

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

定位流程使用的是一组承担不同子任务的工具，并不要求部署一个独立的“定位平台”。这里定位的目标是选出可能缓解压力且允许处理的候选，不承诺查明根因。表格是职责分解，不是五套互斥方案，也不是要求每次调用全部工具。

首先，定位通过观测模块提供的数据，或通过平台HTTP API获取既有证据。Beszel API可读取记录，Prometheus HTTP API返回指标或计算结果。程序处理结构化字段，同时核对对象身份、时间与数据有效性。这一步复用观测成果，避免每次重新采集。没有平台也可使用观测模块在本机采集并保存的数据。

其次，PromQL是Prometheus的查询语言，可以计算变化、按条件筛选和按数值排序，例如得到容器B的内存增长较高这一证据。表达式必须自己配置，容器指标由采集器提供，内存变化不能混用累计计数器速率口径。结果只是数值筛选，不是自动授权。使用Beszel时，同类复杂计算可由本机程序根据可用历史补充；已有Zabbix也可复用计算项和触发器作为线索。本页集中展示一条可理解的工具链，不否认这些替代能力。

Docker Engine的容器Inspect接口或docker inspect命令用于核对完整容器ID、运行状态与标签，关联业务对象。命令默认返回JSON，可供程序读取。标签属于元数据，只有公司维护并核验的配置才能作为权限依据，不能把标签自动视为可信授权。

如果既有容器数据不能解释主机压力，再按需使用pidstat、/proc补充宿主机进程CPU、内存或IO信息。pidstat属于sysstat工具集，不能假设目标Ubuntu已经安装。进程指标与容器统计口径不同，PID到容器仍需关联。当前手册中的新输出选项不代表Ubuntu 22.04所装版本都支持；本页不依赖其JSON选项。补查是获取证据，不会自动完成根因诊断。复杂根因分析可能还需日志或专门性能分析工具，不纳入第一版紧急候选筛选的必选链路。

最后，公司提供保护名单、业务优先级和允许动作，本机规则使用这些配置及指标，过滤对象并生成候选。假设B是允许中断的离线任务而A是受保护数据库，规则才能把B列为候选。是否预计能缓解压力也需要规则和验证，不能把占用最多直接等同于必须停止。自研重点是条件、优先级、无候选分支、数据有效性和身份关联，工具不替公司决定业务取舍。

最终输出是结构化候选，如容器ID、指标依据、规则编号和建议动作，也可以返回无候选。处置模块仍需执行前复核。观测说B增长多是证据，定位说B符合本次候选规则才是决策。以上是待验证方案，没有实施或性能测量。

# 15_actions

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

处置接到的是一个候选，而不是可以立即执行的命令。它的目标是在授权范围内缓解风险，并用新的资源与业务状态确认结果。

执行前重新确认内存风险仍然存在、B还是原来的容器、最新业务权限允许停止，并检查是否已有相同动作在进行。风险消失就取消，目标变化就返回定位；过期告警不能直接触发危险动作。

确认后通过Docker执行约定动作，并设置等待时间和尝试上限。Docker停止通常先发送配置的停止信号，等待宽限期后可能强制终止，因此强制终止是否允许也要写入业务约定。CPU争用可以限制用量，内存紧张可能停止可中断任务；磁盘满则必须另有明确的清理范围，不能把停止当成通用方案。动态降低内存上限也不是无风险的内存释放办法。

执行成功之后重新读取内存压力，并检查关键业务。命令返回成功仅表示操作完成，不能证明整机风险已经缓解。理想输出是B已停止、压力下降且关键业务恢复；如果动作失败或没有改善，就记录并按预定路径升级，不无限重试或不断停止更多对象。

什么时候恢复任务、什么时候解除限制，也要有公司认可的条件。恢复前设置冷却，协调Docker和systemd等自动拉起机制，并记录触发原因、对象身份、动作以及前后结果。这些能力是否由配置完成、由流程编排完成，或需要自己写代码，下一页用同一组问题比较。

示例结果字段描述成功分支，不是实际执行记录。失败或无改善分支也应输出结构化状态和原因。

# 16_action_tools

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

本页具体说明处置可以复用哪些接口和工具。这些是按任务组合的组件，不是五套互斥方案，也不要求全部安装。输入是定位生成的结构化候选，包括对象ID、指标依据、规则编号和建议动作。候选不是立即执行的命令。

执行前使用Docker容器Inspect接口核对完整身份和当前状态，读取本机Linux指标复核压力，例如/proc/meminfo和/proc/pressure/memory。同时重新检查公司配置中的允许动作、保护名单和当前执行策略，任何一项不满足就退出或升级。接口不会自动完成授权判断。

动作层复用Docker Engine对应API或docker update、stop、restart命令。update可调整支持的资源限制，stop停止指定容器，restart重启指定容器。实际动作及参数必须预先允许，并在目标版本验证。降低内存上限可能有副作用，重启也不保证缓解问题；本页不将这些动作视为可以随意互换。stop在宽限期后可能升级为SIGKILL，许可必须覆盖该行为。宿主机systemd服务可用systemctl或D-Bus控制，但本方案以Docker容器为主要对象，因此未放入表格主行。

并发和等待控制可复用flock及HTTP客户端的超时机制。flock提供协作式文件锁，只有使用同一锁协议的本机执行器才能互斥，不能控制所有外部人工操作，也不是跨机器分布式锁。获取锁的等待超时、API请求超时和Docker停止宽限期是不同概念。客户端超时不能保证服务端动作已经取消，超时后应先查询状态，避免盲目重试。冷却时间、跨调用次数上限和动作记录仍需执行器维护，不能把锁和超时说成完整防重复能力。

已有多步运维流程时可选择Ansible Playbook，利用条件、等待、重试和失败分支编排操作。核对、执行和检查任务仍需定义，跨运行互斥需另加控制。中心Ansible不是本机常驻紧急保护的必选依赖。本机紧急流程不应只等待中心下发。已有Monit可用于固定服务检查和恢复，已有Zabbix可用动作触发预配置命令，这些是按现有资产复用的备选，不替代底层动作接口和业务规则。

恢复检查同时关注资源和业务。Docker HEALTHCHECK依赖我们提供的检查命令，其结果只代表该探针覆盖的范围；没有配置就没有这项信号。通过Docker Inspect可读到已配置的健康状态。停止B后不要求B健康运行，而应检查主机压力和受保护的关键业务。应用健康接口、错误率、延迟或任务进度等应按业务选择，与本机资源指标共同验证。程序定义阈值、观察窗口、成功条件以及无改善时的升级方式。告警消失或命令返回成功都不单独证明恢复。

最终输出结构化的执行状态、动作前后指标、业务检查结果和失败原因，并留操作记录。自研重点是授权复核、动作参数、冷却与次数控制、恢复标准及失败升级。以上是候选设计，未在目标服务器部署或实测。

Beszel可以复用基础主机与容器用量、历史、集中查看和告警，也提供PocketBase REST API读取已保存记录，因此不能把它写成只有图表、程序无法利用。本方案让本机程序完成紧急检测和候选判断，需要时读取历史；缺少的细项、短期采样或历史处理按实际需要补充。API结构和记录时效要核对实际版本。

# 19_prometheus

本页仅在现成策略仍有明确覆盖缺口时展开。已被现成策略覆盖的功能可直接复用，不要求全部重新开发。

这一条候选路线使用Prometheus配合本机保护程序。它可以承担持续采集后的历史保存、查询计算和告警条件判断，让本机程序复用计算后的证据。自动处置所需的业务授权、身份复核、动作控制和恢复检查仍要完成。

每台服务器可以部署node_exporter提供主机资源和压力指标，cAdvisor提供容器用量与CPU限流等信息。主机压力不是某个容器的根因证明。请求耗时、错误率或任务积压需要应用或相应采集器提供，安装Prometheus不会自动得到这些业务信息。Docker二十九与cgroup第二版组合下的指标、权限和容器发现必须验证。

本页示例由一个集中部署的Prometheus定期拉取指标、保存时间序列。本机程序通过HTTP API提交PromQL查询，得到增长筛选或组合条件的结果。常用表达式也可以通过记录规则定期计算并保存结果；告警规则则判断何时产生告警。表达式、样本口径和标签对应关系都要配置，并不是平台自动知道应该如何判断风险。Prometheus也能选择其他部署位置，官方所说每个服务独立运行，不等于跨机网络中断后还能获得远端新样本。

本机程序读取公司维护的业务权限，结合平台结果与本机当前状态选出候选，复核后调用Docker接口执行动作，再检查资源与业务恢复，并记录结果。必要的紧急检测保留在本机；平台不可用或数据过期时，不把缺失当作正常，也不按过期排名停止容器，应走事先验证过的本机判断或告警退出路径。

Grafana和Alertmanager按实际需要加入。Grafana供人员查询、展示、探索和告警；Alertmanager负责告警分组、去重和通知。通知去重不等于动作去重，不能代替执行器的互斥、冷却和重试控制。第一版可以先验证查询取数，不强制把每个动作都串在通知之后。需要配置的主要内容是采集目标、标签、查询与告警规则、历史保存时间和访问权限。以上是待验证设计，没有部署或性能实测。

本机补充程序只承担缺口，需与资源限额、日志轮转和已有应急机制协调。来源：https://prometheus.io/docs/introduction/overview/ 和 https://prometheus.io/docs/prometheus/latest/querying/api/ 。Grafana能力参见 https://grafana.com/docs/grafana/latest/introduction/ 。

文档证明功能存在，不能证明在当前服务器上已经配置正确，也不能证明业务恢复、性能开销或故障时效。示例中的容器、业务权限和阈值不是生产配置，已有平台按条件假设理解。下一步必须通过现场配置核验和试点补充证据。
