内存 vs CPU：资源管理"全套方案"对照
左列为本文档的内存兜底工具，右列为 CPU 的对应手段。处置范式不同：内存靠"杀"，CPU 靠"限"。
内存 = 存量资源 → 处置=杀
耗尽即灾难（分配失败→内核 OOM）；不释放就一直占用，必须"杀"来回收。
CPU = 可再生流量 → 处置=限
过载只是排队变慢、不崩溃不丢数据；限流/降权立即见效，无需杀。
内存（本文档）
CPU（对应方案）
① 内核默认机制（兜底底座）
内核 OOM Killer
最后一道保险，按 oom_score 挑进程强杀。
CFS 调度器 + nice + 负载均衡
默认公平分时，天然兜底，通常无需干预。
② 监控 / 触发信号
内存 PSI、swap 用量、MemAvailable
压力信号触发处置。
CPU PSI（/proc/pressure/cpu）、利用率、负载
同样有压力信号，可作触发源。
③ 组级管控（cgroup）
systemd-oomd
按内存压力/swap 触发，处置整个 cgroup（组内全杀）。
cgroup v2 cpu 控制器
cpu.max 硬上限、cpu.weight 权重；systemd 侧 CPUQuota= / CPUWeight= / AllowedCPUs=。
④ 进程级工具
earlyoom
按 oom_score 挑进程，SIGTERM/SIGKILL。
nice/renice · cpulimit · taskset
调优先级；限进程 CPU 占用率；绑核/亲和性。
⑤ 复杂策略引擎
Meta oomd（Detector + Action 插件）
基于 PSI，而 PSI 本身覆盖 CPU/内存/IO，可扩展。
systemd 统一资源控制 / 容器编排
K8s CPU requests & limits、Docker --cpus。
⑥ 最后兜底手段
SIGKILL 强杀（组内全杀）
紧急兜底，不给优雅停机机会。
RT 节流（sched_rt_runtime_us）+ cpu.max 硬上限 + watchdog
防实时任务饿死他人；节流到趋近停止；防饿死检测。
三条要点
① 内核没有也不需要"CPU OOM Killer"：CPU 过载不触发不可恢复失败，CFS 天然公平。② 想抄本文档作业：systemd-oomd 没有 CPU 版官方守护进程，需基于 /proc/pressure/cpu 自建"监控+触发"（Meta oomd 的插件框架就是现成模板）。③ "只选一个主责"同样适用：CPUQuota、cpulimit、编排器限流叠着用会互相干扰，处置顺序要先设计。
