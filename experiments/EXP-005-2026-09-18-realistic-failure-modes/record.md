# EXP-005：真实故障模式验证（多容器竞争 / I/O 饱和 / PID 耗尽）

- 实验 ID：`EXP-005`
- 状态：`PASSED`
- 创建日期：2026-09-18
- 最近更新：2026-09-18
- 关联 Goal：`Goal 2 补充 / 真实故障模式`
- 实验负责人：当前电脑 WSL2（由 agent 执行）
- 环境：4 CPU / 3.9 GB RAM / 2 GB swap（受限 WSL2）

## 1. 实验目的

EXP-004 证明了单进程资源高压下 SSH 仍可用。本实验验证更接近生产现实的故障模式：

1. **F1** 多容器同时竞争内存（4 容器 × 1.2 GB = 4.8 GB 请求，系统仅 3.9 GB）
2. **F2** 磁盘 I/O 饱和（4 个 fio 并行 random 4K rw，iodepth=32）
3. **F3** PID 耗尽（4 容器各 spawn 3000 进程 = 12000），并验证 `--pids-limit` 保护效果

## 2. 结果

### 2.1 F1 多容器内存竞争

| 指标 | 值 |
| --- | --- |
| 容器数 | 4 |
| 请求总内存 | 4.8 GB（系统仅 3.9 GB） |
| 峰值系统内存 | **94%** |
| 峰值 Swap | **85%**（1733 MB / 2048 MB） |
| 容器 OOM killed | 全部 false |
| SSH 延迟 | 118–480 ms，全部成功 |
| 容器存活 | 全部 running |

**结论**：4 个容器同时竞争超过系统总量的内存，内核通过 swap 分配管理了竞争，没有触发 OOM kill。SSH 全程可用。

### 2.2 F2 磁盘 I/O 饱和

| 指标 | 值 |
| --- | --- |
| fio 配置 | 4 容器 × random 4K rw, iodepth=32, direct=1 |
| I/O PSI avg10 | 0.10%（**WSL2 虚拟 NVMe 太快，未能饱和**） |
| SSH 延迟 | 159–586 ms（比 CPU/内存测试波动更大） |
| SSH 成功率 | 100% |

**结论**：WSL2 的虚拟磁盘性能太高，fio 无法饱和。SSH 延迟波动比其他测试更大（峰值 586 ms），暗示 I/O 争用有一定影响，但在 NVMe 上不足以导致 SSH 失败。生产环境使用 SATA SSD 或 HDD 时需要重新测试。

### 2.3 F3 PID 耗尽

#### F3a：无 PID 限制

| 指标 | 值 |
| --- | --- |
| 容器数 | 4 |
| 每容器进程数 | 3000 |
| 系统总进程 | **12,051**（基线 64） |
| 内核 pid_max | 4,194,304 |
| PID 占用率 | 0.3%（远未耗尽） |
| 内存 | 57%（12000 个 sleep 进程） |
| SSH 延迟 | 117–390 ms，全部成功 |

#### F3b：有 `--pids-limit=100` 保护

| 指标 | 值 |
| --- | --- |
| Docker --pids-limit | 100 |
| 系统总进程 | 438（vs 无限制的 12051） |
| 容器内 exec | **失败**（Resource temporarily unavailable，容器已达 PID 限制） |
| SSH 延迟 | 128–308 ms，正常 |

**结论**：
1. 无限制时 12000 个进程仅占内核 PID 上限（4M）的 0.3%，SSH 不受影响。要真正耗尽 PID 需要 400 万个进程（fork bomb 级别）。
2. **`--pids-limit` 是有效的资源边界**：容器内进程被严格限制在 100 个以内，甚至无法执行新命令。这证明 Docker 的 PID 限制可以防止容器级 fork bomb 逃逸影响宿主机。

## 3. 综合结论

### SSH 从未失败的根因分析

| 保护层 | 机制 | 在测试中的表现 |
| --- | --- | --- |
| 内核 CFS 调度器 | 公平分配 CPU 时间片 | CPU 400% 时 SSH 仍获得调度（延迟增加但不失败） |
| 内核内存管理 | swap + page cache 回收 | 92% 内存 + 98% swap 时系统继续运行 |
| 内核 OOM killer | 内存耗尽时选择牺牲者 | 杀掉压力进程，保护了 sshd |
| Docker 资源限制 | --memory/--cpus/--pids-limit | 有效隔离容器内资源消耗 |

### SSH 会在什么条件下真正失败

基于本轮测试的推断（未实测）：

| 条件 | 可能性 | 原因 |
| --- | --- | --- |
| 内核 OOM killer 选中 sshd | 低（但可能） | OOM killer 按 oom_score 选victim，sshd 通常不是最高分，但在多进程竞争时不保证 |
| PID 耗尽（fork bomb） | 需 400 万+进程 | 内核 pid_max 太高，正常容器无法达到 |
| 磁盘 I/O 完全饱和 | 需物理 HDD/SATA SSD | WSL2 NVMe 太快 |
| 网络饱和 | 未测试 | 需要流量生成工具 |
| 内核 bug / panic | 极低 | 但生产环境的旧内核（6.8）可能有不同行为 |

### 项目价值重新定位

1. **预防比救援更有价值**：如果每个 Docker 容器都设置了 `--memory`、`--cpus`、`--pids-limit`，资源竞争危机基本不会发生。这比事后救援更有效。
2. **监控的价值是提前发现**：Beszel 能在资源达到临界前发出告警，让人有时间介入。
3. **Guardian 的核心价值是"有人忘了设限制"的兜底**：当某些容器没有资源限制且开始无界增长时，Guardian 的保护名单和受控终止是最后防线。
