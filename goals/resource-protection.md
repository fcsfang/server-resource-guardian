## Goal 1：两层资源保护方案测试

- 状态：`PLANNED`
- 创建日期：2026-09-17
- 最近更新：2026-09-17
- 负责人：双机协作；本地电脑负责 PoC，办公电脑负责生产事实、leader 沟通和同步
- 来源：[Leader 最新测试交接](../docs/13-leader-test-handoff.md)

### 目标结果

在获得非生产测试机、故障注入和动作授权后，分别验证：

1. **第一层：救援能力保障**——CPU 或内存高压下，管理员仍能新建 SSH 连接、执行诊断命令并停止测试中的异常任务。
2. **第二层：自动资源保护**——先验证现成策略能否按明确规则观测、定位、选择允许处理的对象、执行受控动作并验证结果；只有现成能力不足时，才整理 Guardian 的最小开发缺口。

本目标不承诺避免所有宕机，不在生产机直接注入故障，不默认启用真实终止、重启或资源变更。

### 任务清单

- [ ] **G1-T01**：确认非生产测试机、OS/内核/systemd/cgroup/Docker 版本和故障注入授权。
- [ ] **G1-T02**：确认 SSH 失效的真实表现、救援链路、测试对象和停止条件。
- [ ] **G1-T03**：建立无保护配置下的 SSH、shell、诊断命令和停止测试任务基线。
- [ ] **G1-T04**：在有界测试对象内执行 CPU 压力测试，比较资源边界/权重配置对救援链路的影响。
- [ ] **G1-T05**：在有界测试对象内执行内存压力测试，比较内存边界/保护配置和实际救援表现；不把 CPU 优先级当作内存解决方案。
- [ ] **G1-T06**：只读验证第二层的压力观测、对象定位、现场快照和现成策略触发条件。
- [ ] **G1-T07**：经明确授权后，使用可丢弃测试对象验证自动策略的选择、动作、审计、恢复和冷却；未授权时使用模拟动作。
- [ ] **G1-T08**：每个实验生成 `EXP-###` 记录，脱敏核心数据放入 `experiments/<experiment-id>/data/`，结论回链到本 Goal 和 `PROGRESS.md`。
- [ ] **G1-T09**：根据实测结果判断“现成策略已足够”或“需要 Guardian 的最小缺口”，不直接扩展为完整平台开发。

### 接手入口

新 agent 先阅读：

1. `PROGRESS.md`
2. 本文件
3. `docs/13-leader-test-handoff.md`
4. `docs/07-poc-blueprint.md`
5. `docs/05-open-questions.md` 和 `docs/06-safety-policy.md`

接手后的第一步是补齐 `G1-T01`、`G1-T02` 的信息，不要直接连接生产服务器或启动自动处置。已执行的实验只能以 [`experiments/`](../experiments/README.md) 中的记录为准。

### 完成标准

- [ ] 两层方案的测试环境、授权、保护名单和停止条件均有记录。
- [ ] 第一层 CPU、内存压力场景均有基线、配置对照、救援链路结果和资源开销数据。
- [ ] 第二层至少完成一轮只读/模拟验证，明确现成策略的覆盖范围和缺口。
- [ ] 每个结论都有实验记录或外部证据，不把计划值写成实测值。
- [ ] 没有发生未授权的生产变更、真实误杀或不可回滚动作。
